data/analytics · Grafana · Skill Leaf

The dashboard layer
that doesn't own your data.

Grafana queries other people's databases and draws the result. That one design decision — no storage of its own — is why it ended up on top of almost every operational stack, and it is also the thing that decides whether it suits your build or doesn't.

01 · What it is

A query-and-draw layer, not a BI platform.

Grafana is a dashboard and alerting tool that stores no data of its own. You register data sources — Prometheus, PostgreSQL, ClickHouse, Loki, InfluxDB, Elasticsearch, a plain HTTP endpoint — and each panel on a dashboard is a query sent live to one of them. Grafana keeps the dashboard definitions, the users, the alert rules and the data-source credentials, and nothing else. Every number you see was fetched when you loaded the page.

That is a genuinely different product from a BI platform, and the distinction gets blurred often enough to cause bad tool choices. Superset or Metabase are built around a semantic model: you define datasets, and analysts explore them without writing SQL. Grafana assumes you already know the query. Its strength is time — a panel is overwhelmingly "this metric, over this window, refreshed every fifteen seconds" — and its natural reader is someone watching a system rather than someone analysing a business.

Get that right and the tool choice is easy. Grafana is for operational data that changes while you watch it. If the question is "is the service healthy, and what happened at 02:40", it is the best tool available. If the question is "what did margin do by product line last quarter", it is the wrong one, and you will feel that within a week of trying.

The LGTM stack, since the names come up constantly

Grafana Labs ships four open-source backends that pair with Grafana, and the acronym for them is LGTM. Loki for logs, Grafana for the dashboards, Tempo for distributed traces, Mimir for metrics at scale — Mimir being the Prometheus-compatible long-term metrics store that succeeded Cortex. You do not need any of them: Grafana over Prometheus and Postgres is a perfectly ordinary deployment. But the four are designed to work together, and when someone says "we run the LGTM stack" this is what they mean.

02 · How it works

Data sources, panels, variables, alerts.

Four concepts. Learn the third one properly and you build one dashboard instead of twenty.

Data sources are connections Grafana holds, each with its own credentials and query editor. A single dashboard can mix them — a panel from Prometheus next to a panel from Postgres — which is often the reason Grafana wins over a tool tied to one warehouse.

Panels are a query plus a visualisation. The query is written in the source's own language: PromQL for Prometheus, LogQL for Loki, plain SQL for Postgres and ClickHouse. There is no abstraction layer over them, which is both the appeal and the reason non-technical users stall.

Template variables are the concept worth the most. A variable is a value chosen from a dropdown — a tenant, an environment, a host — that the panel queries interpolate. Build the dashboard once with a $tenant variable and you have one dashboard serving every client, instead of a copy per client that drifts out of sync. Teams that skip variables end up maintaining dozens of near-identical dashboards, and that is the most common self-inflicted Grafana problem we see.

Alerting evaluates a query on a schedule and fires when a condition holds. The current unified alerting system is a real improvement on what came before, but it is still a scheduled query, which means an alert can only see what the data source retained — a point worth remembering before trusting it as a safety net.

Dashboards are JSON underneath, and that is the part to use deliberately. Provisioning them as files in a repository, rather than clicking them together in the UI, makes them reviewable, diffable and reproducible across environments. It is the difference between a dashboard someone built and a dashboard the team owns.

# Provision data sources as files, not by clicking. Keep this in the repo.
# /etc/grafana/provisioning/datasources/sources.yaml
apiVersion: 1
datasources:
  - name: Prometheus
    type: prometheus
    url: http://prometheus:9090
    isDefault: true
  - name: ClickHouse
    type: grafana-clickhouse-datasource
    jsonData:
      host: clickhouse.internal
      port: 9000
    secureJsonData:
      password: ${CLICKHOUSE_PASSWORD}   # from the environment, never in the file

# A panel query against ClickHouse, using a template variable.
# $tenant comes from a dropdown; $__timeFilter is Grafana's time range.
SELECT
  toStartOfFiveMinute(occurred_at) AS time,
  count() AS events
FROM events
WHERE tenant_id = ${tenant} AND $__timeFilter(occurred_at)
GROUP BY time ORDER BY time
03 · The licence

AGPLv3, and why it belongs in a client conversation.

This is the part that gets skipped, and it is the part that occasionally makes Grafana the wrong choice for reasons that have nothing to do with the software.

In April 2021 Grafana Labs relicensed Grafana, Loki and Tempo from Apache 2.0 to AGPLv3. The first affected releases were Grafana 8.0, Loki 2.3 and Tempo 1.0 — anything on Grafana 7.x or older remains Apache-licensed. Mimir was AGPLv3 from the start. Grafana Enterprise and Grafana Cloud are offered under a separate commercial licence, and plugins, agents and some libraries stayed Apache. The company's stated reason for choosing AGPLv3 over SSPL was that AGPLv3 is OSI-approved and SSPL is not, which is a more honest position than several comparable relicensings.

What AGPLv3 actually obliges: if you modify Grafana and offer the modified version as a service over a network, you must make the complete source of your modified version available to its users. That is the network clause, and it is narrower than people fear. Running unmodified Grafana — self-hosted, behind your VPN, for your own staff or embedded in your own product — triggers nothing. Writing a plugin, provisioning dashboards, theming it, or putting it behind your own authentication proxy is not modifying Grafana.

Where it genuinely matters is twofold. First, if you intend to fork or patch Grafana itself and ship that as part of a hosted product, get legal advice before you start — that is the exact case the licence was changed to cover. Second, and more common in practice: some corporate and public-sector procurement policies in South Africa prohibit AGPL-licensed software outright, regardless of whether the obligation would ever bind. That is a policy fact rather than a legal one, and arguing the licence's merits with a procurement committee is not a winnable fight. Find out before you build the dashboards, not after.

We have seen it claimed that Grafana Enterprise can be run without a licence by organisations whose policy forbids AGPL. We could not confirm that against a primary Grafana Labs source and would not act on it — if an AGPL prohibition is the blocker, talk to Grafana Labs about the commercial licence rather than relying on a secondary account.

They are not alternatives, and most stacks run both

The common mature arrangement is Grafana for the operational surface — infrastructure, service health, pipeline freshness, alerting — and Superset for the business surface over the warehouse. Trying to make one do both is how you end up with a Grafana full of unmaintained business dashboards nobody trusts, or a Superset being refreshed every thirty seconds by someone watching a deployment.

05 · SA context

Self-hosting, residency and the licence question locally.

Self-hosting is the sensible default here, and it is genuinely easy. Grafana is one container with a small database behind it — SQLite for a single instance, Postgres for anything you care about. It is one of the lowest-effort self-hosted services in this tree, which matters when the alternative is a dollar-billed subscription that scales with users and metric volume. Grafana Cloud is a good product; it is also an FX-exposed monthly cost for something a modest VM runs comfortably.

Residency falls out of the architecture. Because Grafana stores no data of its own, the residency question is about the data sources, not about Grafana. A self-hosted Grafana querying a ClickHouse and a Postgres that both sit in South Africa means no personal information crosses a border to be visualised. Grafana Cloud inverts that: your queries, and the results they return, leave the country. For dashboards over operational metrics that is often immaterial; for dashboards over anything containing personal information it is a POPIA cross-border question you now have to answer. Check what your panels actually return before assuming it is only metrics.

Credentials are the real risk, and it is underrated. A Grafana instance holds connection credentials to every data source it can see — frequently including production databases. It is, in effect, a directory of your most sensitive credentials with a web interface. Put it behind SSO rather than local accounts, scope every data-source user to read-only on the specific tables it needs, and treat a Grafana compromise in your incident planning as equivalent to a database compromise. Under POPIA section 19 that scoping is part of the "appropriate, reasonable technical measures" you are obliged to take, not an optional hardening step.

Load shedding is the one thing Grafana is genuinely good at showing you. Dashboards over UPS state, generator fuel, link status and queue depth during an outage are the most valuable panels many South African operations have, and they are exactly the real-time operational shape Grafana is built for. The obvious trap: host the Grafana that monitors your infrastructure somewhere other than on that infrastructure, or it goes dark precisely when you need it.

06 · Gotchas

Things that only bite once you ship.

Dashboards built in the UI are not reproducible

A dashboard clicked together in the browser exists in one database with no history and no review. Export the JSON and provision it from the repository. Otherwise the person who built it is the only one who can fix it, and the staging copy will never match production.

It will take your database down if you let it

A heavy panel on a thirty-second refresh, open on ten screens, is a sustained query load nobody authorised. Set generous refresh intervals, enable query caching where available, point panels at pre-aggregated tables rather than raw events, and apply per-user limits on the data source itself.

No variables means dashboard sprawl

Copying a dashboard per tenant or per environment feels faster on day one. Six months later there are forty of them, they have diverged, and a fix has to be applied forty times. Build with template variables from the first dashboard.

SQLite is not a production backend

The default SQLite store is fine for one instance on one host. It will not survive running two replicas, and it makes backup and migration awkward. Move Grafana's own state to Postgres before anyone depends on the dashboards.

Alerts only see what the data source kept

An alert is a scheduled query. If the metric was never scraped, or retention has already aged it out, the alert cannot fire and its silence looks identical to health. Alert on the absence of data too, not only on bad values.

The AGPL question is a procurement question

Technically the obligation rarely binds. Practically, "no AGPL software" appears in real corporate and public-sector policies. Ask at the start of the engagement, because discovering it after the dashboards are built is an expensive conversation.

07 · Decision guide

Use it for, skip it for.

Grafana is close to unbeatable at operational dashboards and genuinely poor at business intelligence. The honest version of this guide is mostly about not mistaking the second for the first.

Use Grafana when

  • The data is time-series and operational — infrastructure, service health, queue depth, device telemetry, pipeline freshness.
  • Someone needs to watch it change, with a refresh interval rather than a report schedule.
  • You need alerting attached to the same queries that drive the dashboards.
  • One view has to span several systems — Prometheus and Postgres and ClickHouse on one screen.
  • The audience writes queries, or will accept dashboards built by people who do.
  • Self-hosting matters: residency, no dollar subscription, one container to run.

Skip Grafana when

  • The users are analysts who need to slice data themselves without SQL. Use Superset or Metabase — this is not a Grafana weakness you can configure away.
  • The output is a formatted business report — financial statements, board packs, anything that needs to print properly.
  • You need a governed semantic layer so that "revenue" means one thing everywhere. Grafana has no such concept.
  • The organisation's procurement policy prohibits AGPL-licensed software and a commercial licence isn't on the table.
  • The data isn't time-shaped at all. A table of current stock levels does not need a dashboard with a time picker.
  • You want it to store the data too. It doesn't, and no configuration makes it.
08 · 2ⁿ Perspective

How this leaf compounds in the tree.

Grafana is where the other nodes become visible. That is a smaller claim than it sounds and a more useful one.

Every operational node in this tree produces something worth watching, and almost none of them produce a way to watch it. A ClickHouse cluster has merge lag. A Frappe site has background-job queues. A Cloudflare Worker has request and error rates. An agent pipeline has token spend and failure rates per step. Each of those is a number somewhere that nobody looks at until it has already caused an incident. Grafana is the cheapest way to turn all of them into one screen, and the fact that it stores nothing is why it can sit over all of them at once.

For agent work there is a sharper version of this. Agent systems fail quietly — a step that silently retries, a tool call that returns an empty result, cost that drifts upward over weeks. The instinct is to build bespoke observability into the agent. The cheaper move is to write the metrics somewhere Grafana can query and put an alert on the shape you care about, because the dashboard layer is already a solved problem and the agent's own behaviour is not.
