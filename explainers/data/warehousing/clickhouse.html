data/warehousing · ClickHouse · Skill Leaf

Analytical queries
that stay fast under load.

ClickHouse is a columnar OLAP database built for one job: aggregating over very large tables, repeatedly, while many clients watch. It is the answer when Postgres materialised views have stopped keeping up and a dashboard needs to stay responsive at the same time.

Live Apache 2.0 Columnar OLAP Self-host or Cloud Last updated · Nov 2026
01 · What it is

A database that gave up transactions to win at scans.

ClickHouse is an open-source columnar database for online analytical processing. The design is unapologetically specialised: store each column separately and compressed, read only the columns a query names, process them in vectorised batches, and accept an append-oriented write model in exchange. What you get is aggregation over billions of rows in the time a row store takes to warm up. What you give up is the thing a transactional database is for — you do not get the update-and-delete ergonomics, the foreign-key enforcement or the transactional guarantees that PostgreSQL hands you for free.

That trade is the whole point, and it tells you when the tool is right. ClickHouse is for event data, logs, metrics, clickstreams, telemetry, financial tick data, call records — anything that arrives continuously, is written once, is read in aggregate, and is never really edited afterwards. It is not for an order table that people amend.

The piece that distinguishes it from DuckDB, the other columnar engine in this sub-hub, is concurrency. DuckDB is a library in one process with a single writer. ClickHouse is a server built to hold many concurrent connections, each running an analytical query, continuously, for as long as the service is up. If the question is "can a hundred people hit this dashboard at once", that is the line that separates them.

The honest sizing question first

ClickHouse is genuinely excellent, and it is also a real piece of infrastructure to run. Before reaching for it, check whether PostgreSQL with well-chosen indexes and materialised views actually fails for your workload, because for a surprising share of "we need a warehouse" conversations it doesn't. The signals that it genuinely has stopped being enough are concrete: aggregate queries that take tens of seconds and can't be pre-computed, a table in the hundreds of millions of rows that keeps growing, and concurrent dashboard users who feel each other's queries.

If instead the analysis happens in one process on an export, read the DuckDB leaf — it does that job with no service to operate.

02 · How it works

MergeTree, and why the name tells you the model.

Almost everything about operating ClickHouse follows from one table engine family.

Tables in a self-managed ClickHouse are overwhelmingly MergeTree family. An insert writes a new immutable data part, sorted by the table's sorting key. Background threads then merge small parts into larger ones, continuously, which is where the name comes from. Queries read the parts they need, skipping whole granules using the sparse primary index. Understanding that single mechanism explains most of the operational behaviour you will encounter: why many small inserts are harmful, why the sorting key matters more than any index you are used to, and why "the merges are behind" is a thing you will eventually monitor.

For replication the family member is ReplicatedMergeTree, and coordination between replicas is handled by ClickHouse Keeper — a Raft-based coordination service that replaced the earlier ZooKeeper dependency. A production self-hosted deployment is therefore at minimum: ClickHouse nodes, a Keeper quorum, and a backup mechanism you assemble yourself, commonly clickhouse-backup on a schedule.

The specialised variants of MergeTree are where most of the real gains are, and they are worth knowing by name before you design a schema: ReplacingMergeTree for deduplicating on a key, SummingMergeTree and AggregatingMergeTree for pre-aggregation at merge time, and materialised views that write into them so that the aggregate is maintained on insert rather than computed on read.

-- The sorting key is the single most consequential schema decision.
-- Order it by how you filter, coarsest first.
CREATE TABLE events (
  tenant_id   UInt32,
  occurred_at DateTime,
  event_type  LowCardinality(String),
  amount_zar  Decimal(12, 2),
  payload     String CODEC(ZSTD(3))
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(occurred_at)
ORDER BY (tenant_id, occurred_at)
TTL occurred_at + INTERVAL 25 MONTH DELETE;

-- Pre-aggregate on insert, not on read.
CREATE MATERIALIZED VIEW daily_totals
ENGINE = SummingMergeTree
ORDER BY (tenant_id, day) AS
SELECT tenant_id, toDate(occurred_at) AS day, sum(amount_zar) AS total
FROM events GROUP BY tenant_id, day;

-- Insert in batches. Thousands of rows per statement, not one.
INSERT INTO events SELECT * FROM input('...');
03 · Self-hosted vs Cloud

The two ClickHouses are not the same database.

This is the decision that shapes everything else, and the marketing on both sides obscures the one asymmetry that matters.

Self-managed ClickHouse is Apache 2.0, runs on your own hardware or VMs, uses local or attached storage with MergeTree-family engines, and leaves backups, replication topology and monitoring to you. ClickHouse Cloud is the vendor's managed service, and it does not merely host the same thing: it separates compute from shared object storage using SharedMergeTree, an engine available only in the managed service. There is no path to running SharedMergeTree yourself.

That asymmetry is the part to internalise. It is not a feature flag — it is a different storage architecture, and it is the one that delivers the managed service's elasticity. It also means the migration between the two is not symmetric: moving onto Cloud is far easier than moving off it, and Cloud's egress charges on data leaving the service make a later exit a line item rather than an afternoon. Judge the lock-in on that basis rather than on the licence, which is permissive on the self-managed side.

The published comparisons also disagree substantially on where self-hosting becomes cheaper — we have seen the crossover put anywhere from a few hundred dollars a month to tens of terabytes stored. We would not repeat any of those numbers as a rule. The reliable version is unglamorous: the cost that decides this is operational, not infrastructural. If you have a platform team that already runs stateful services, self-hosting is a known quantity. If you don't, the managed service is buying you the team you don't have, and the sticker price is not what you are actually comparing.

04 · SA context

Residency, FX, and the case for self-hosting here.

Residency is the strongest local argument for self-hosting. ClickHouse's most natural workloads — call records, transaction streams, clickstream, device telemetry — are frequently full of personal information, and POPIA's conditions on transferring it outside the Republic are the kind of thing that turns a two-week build into a two-month legal exercise. A self-managed cluster in a Johannesburg or Cape Town data centre, or in africa-south1, removes that question entirely. Before assuming the managed service can do the same, check which regions it actually offers; do not infer availability from a provider having a local presence for other products.

FX exposure, stated plainly. A managed analytical service is a dollar-denominated monthly commitment whose rand cost moves with the exchange rate, and it is usage-billed, so the bill grows with the dataset at the same time. Self-hosting converts that into local infrastructure cost plus local engineering time. That is not automatically cheaper — engineering time is expensive and scarce — but it is denominated in the same currency as the client's revenue, which materially changes how a CFO reads it. Where Cloud is the right answer, budget at a conservative exchange rate rather than today's and include the egress cost of an eventual exit.

Retention is a compliance control, and TTL is how you implement it. POPIA requires that personal information is not kept longer than necessary. ClickHouse's table-level TTL ... DELETE turns that obligation into a schema declaration that enforces itself at merge time, rather than a deletion script someone has to remember to run. Set it when you create the table and the retention policy becomes a property of the data rather than a promise in a document.

Load shedding and a stateful cluster. This is the part that gets underestimated. A replicated ClickHouse with a Keeper quorum does not enjoy losing power: you need the Keeper quorum to survive the outage, which means an odd number of nodes with genuinely independent power, not three VMs on one host. If the site has load shedding and no generator, either put the cluster somewhere that doesn't, or accept the managed service and its FX exposure. Running a quorum on municipal power alone is how clusters get corrupted.

05 · Gotchas

Things that only bite once you ship.

Most ClickHouse pain is one of two mistakes: writing like it's Postgres, or choosing the sorting key carelessly.

Row-at-a-time inserts will destroy it

Every insert creates a data part. An application doing single-row inserts produces thousands of tiny parts, the merge threads fall behind, and you get the Too many parts error with queries degrading around it. Batch at the application, or use asynchronous inserts, or put a queue in front. This is the single most common way a first ClickHouse deployment fails.

The sorting key is close to permanent

ORDER BY determines physical layout and therefore which queries can skip data. Get it wrong and the fix is recreating the table and backfilling. Choose it from the filters your real queries use, coarsest cardinality first, before you load anything substantial.

UPDATE and DELETE are not what you think

Mutations exist but they rewrite data parts asynchronously — they are maintenance operations, not transactional statements, and they are expensive. There is no rollback. If the workload genuinely needs row-level edits, you have chosen the wrong database; model corrections as new rows with ReplacingMergeTree instead.

No referential integrity, no joins-as-usual

Foreign keys don't exist. Joins work but are not the strength, and a large distributed join will disappoint you compared to the equivalent in Postgres. Denormalise deliberately, and use dictionaries for lookup tables rather than joining to them.

Eventual consistency between replicas is real

An insert acknowledged on one replica is not instantly readable on another. Reading immediately after writing through a load balancer can legitimately return nothing. Use insert_quorum and the sequential-consistency setting where it matters, and design the application not to need read-after-write where it doesn't.

A query can consume the whole server

An unbounded GROUP BY over a high-cardinality column will take all the memory it can and take the node down with it. Set max_memory_usage, max_execution_time and per-user quotas before exposing it to a BI tool, not after the first incident.

06 · Decision guide

Use it for, skip it for.

ClickHouse is the right answer less often than its benchmarks suggest, and when it is right nothing else is close.

Use ClickHouse when

  • The data is append-mostly events at scale — logs, metrics, telemetry, clickstream, transactions, call records.
  • Aggregate queries over hundreds of millions of rows or more need to return in under a second.
  • Many clients need to query concurrently and continuously — a product analytics surface, a customer-facing dashboard.
  • Postgres has demonstrably stopped coping: materialised views can't be refreshed fast enough and indexes aren't helping.
  • POPIA residency means the analytical store has to sit in South Africa, and you have the team to run it.
  • Storage cost matters — columnar compression on event data routinely beats a row store by a wide margin.

Skip ClickHouse when

  • You need transactions, foreign keys or frequent row-level updates. Use PostgreSQL. This is not a tuning problem.
  • The analysis happens in one process over files or an export. Use DuckDB and skip the service entirely.
  • Postgres has not actually failed yet. Indexes and materialised views first; a cluster is not a free upgrade.
  • Nobody on the team has run a stateful distributed service, and the managed service's dollar billing doesn't fit the client's budget. Pick one of the two, not neither.
  • The site has load shedding and no generator, and you were planning to self-host the quorum there.
  • The workload is a handful of analysts running occasional queries. The operational overhead will exceed the benefit.
07 · 2ⁿ Perspective

How this leaf compounds in the tree.

ClickHouse is the node that makes analytical workloads a product surface rather than an internal report.

The reason this leaf matters beyond the data branch is that it changes who analytics can be shown to. A Postgres-backed report is something you run for yourself. A ClickHouse-backed aggregate that returns in under a second, under concurrent load, is something you can put in front of a client inside their own application — per-tenant usage, live operational dashboards, the analytics half of a SaaS product. That is a revenue surface, not a cost centre, and it is the same reason the ERP and construction branches eventually point here.

It also completes the warehousing spectrum. PostgreSQL covers transactional and light analytical in one engine. DuckDB covers analytical work with no service at all. ClickHouse covers analytical work as a service at scale. Knowing which of the three a workload wants — and being able to say so in one sentence — is most of the value of reading all three leaves.
