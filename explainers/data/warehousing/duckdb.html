data/warehousing · DuckDB · Skill Leaf

The warehouse that
runs inside your process.

DuckDB 2.0 LTS — an analytical database with no server, no port and no cluster. It links into your Python, Node or CLI process, reads Parquet and CSV where they already sit, and answers analytical SQL over them at a speed that makes most small warehouses look like overhead.

Live MIT License v2.0 LTS In-process Columnar Last updated · Nov 2026
01 · What it is

SQLite's shape, OLAP's engine.

DuckDB is an in-process analytical database. The comparison everyone reaches for is SQLite, and on deployment shape it's exact: one library, linked into your application, no daemon to run, no credentials to manage, the whole database in a single file or purely in memory. Where it diverges is the engine underneath. SQLite stores rows and is built to fetch a few of them quickly. DuckDB stores columns and is built to scan all of them — vectorised execution, compressed columnar storage, a query optimiser that expects aggregations over millions of rows rather than point lookups by primary key.

That combination solves a problem most data teams have and few name: the analytical workload that is too big for pandas to hold comfortably and far too small to justify a warehouse. A 4 GB Parquet export, a month of transaction logs, a client's entire general ledger. The traditional answer was to provision something — a Postgres with enough RAM, a BigQuery dataset, a Snowflake trial — and then own it. DuckDB's answer is pip install duckdb and a SQL string.

The second thing it does, and arguably the more useful one, is query files in place. You don't load data into DuckDB to query it. You point SQL at a Parquet file, a directory of Parquet files, a CSV, a JSON file, an S3 or R2 bucket, or a pandas DataFrame sitting in the same process, and it reads what the query needs and ignores the rest. There is no ingestion step to build and no copy of the data to keep in sync.

Where this sits against the other warehousing leaves

PostgreSQL is the default for anything transactional and holds up fine for light analytics. ClickHouse is where you go when analytical queries have to serve concurrent users at scale, continuously. DuckDB is the one that isn't a service at all — it is a library you call, which makes it the right tool for notebooks, ETL steps, CI jobs, CLI tools and agent workloads, and the wrong tool for anything multiple clients need to connect to at once.

In practice these compose rather than compete: DuckDB reads the Parquet that a pipeline wrote, transforms it, and hands the result to Postgres or to a dashboard. It is frequently the compute in a stack that has no other compute.

02 · How it works

Point SQL at the files. There is no step one.

Four patterns cover most of what DuckDB gets used for. None of them involve provisioning anything.

The API surface is deliberately small. In Python you get a connection object; in Node, Rust, Go, Java and R you get the equivalent; from the shell you get a CLI that reads SQL on stdin. All of them drive the same engine with the same SQL dialect, which is close enough to PostgreSQL's that most queries move across unchanged.

# 01 · Query a Parquet file with no ingestion step
import duckdb
duckdb.sql("""
  SELECT branch, sum(amount_zar) AS total
  FROM 'exports/ledger_2026_*.parquet'
  WHERE posted_at >= '2026-07-01'
  GROUP BY branch ORDER BY total DESC
""").show()

# 02 · Query a DataFrame already in this process — zero copy
import pandas as pd
df = pd.read_csv("debtors.csv")
duckdb.sql("SELECT account, days_overdue FROM df WHERE days_overdue > 90")

# 03 · Read straight off object storage (R2, S3, GCS)
duckdb.sql("""
  INSTALL httpfs; LOAD httpfs;
  SET s3_endpoint = 'ACCOUNT.r2.cloudflarestorage.com';
  SELECT count(*) FROM read_parquet('s3://warehouse/events/**/*.parquet')
""")

# 04 · Persist to a file when you want the database to outlive the process
con = duckdb.connect("analytics.duckdb")
con.sql("CREATE TABLE ledger AS SELECT * FROM 'exports/*.parquet'")

What 2.0 changed. The 1.0 release in 2024 was about stability and a backwards-compatible storage format; 2.0, released 21 October 2026 as Cinnamon Teal, is explicitly a feature release with LTS support stated through at least October 2027. The two changes that matter operationally are asynchronous I/O for Parquet, CSV and the native storage format — which is what makes reading from object storage over a slow link tolerable rather than painful — and full integration of the VARIANT type introduced in 1.5, for semi-structured data that doesn't have one fixed schema. The 1.5 line also added a native GEOMETRY type and the Quack client-server protocol as a core extension, which is the closest DuckDB comes to being something you connect to over a network. Building from source now needs a C++17 compiler.

DuckLake. Alongside 1.5.2 the project shipped DuckLake 1.0, a lakehouse specification with a reference implementation: table formats and metadata in a catalogue database rather than in a pile of manifest files. If you have been weighing Iceberg or Delta Lake for a small estate, this is the lighter-weight third option, and it is from the same project rather than bolted on.

03 · The AWS question

Amazon bought the company. It did not buy the database.

This is the first thing anyone asks about DuckDB now, and the honest answer has more than one part to it.

On 26 August 2026 Amazon signed a definitive agreement to acquire DuckLabs, the company behind DuckDB, which becomes a wholly owned subsidiary. AWS stated plainly that it is not acquiring the open-source project. The core IP and the trademarks for DuckDB, DuckLake and Quack sit with the independent non-profit foundation, and all three remain under the MIT licence — which, unlike AGPL or SSPL, imposes nothing on you downstream and cannot be retroactively narrowed on code already released.

So the licence risk that killed confidence in other projects after an acquisition is genuinely not the risk here. What remains is roadmap influence, and that is a real thing rather than a hypothetical. Most of the core committers now draw an Amazon salary. The foundation has not finished settling its voting rights and governance structure, and is reportedly considering a technical advisory board to give outside companies a formal channel to the roadmap. Commentary that two of the foundation's three board seats are now held by Amazon employees has circulated but we have not been able to confirm it against a primary source, so treat it as unverified.

Our read, stated as a position rather than a fact: the MIT licence means a bad outcome is forkable, and a project this widely embedded would be forked. The thing worth watching is not the licence but whether features that serve AWS's managed-service interests get priority over features that serve people running DuckDB inside their own processes. That is a question you answer by watching release notes over the next year, not by reading the acquisition announcement.

What this means if you're recommending DuckDB to a client right now

It does not change the recommendation for the workloads below. DuckDB in an ETL step, a notebook or a CLI tool is a library dependency pinned to a version, under a permissive licence, with an LTS line supported into late 2027. The acquisition does not reach into a build like that. Where it should make you pause is a decision to standardise an organisation's whole analytical layer on DuckLake — a younger specification whose governance is genuinely unsettled — when Iceberg has broader multi-vendor backing.

04 · Where it earns its place

The jobs it does better than anything else.

JobWhy DuckDB and not the obvious alternative
The transform step in a pipelineReplaces a pile of pandas with SQL that doesn't need the whole dataset in RAM, and doesn't need a warehouse to run the transform in. Reads Parquet, writes Parquet.
Analysis in a notebookQueries DataFrames in place with no copy, so you can mix SQL and Python without serialising between them. Handles files larger than memory, which pandas does not.
Interrogating a client's data exportA 3 GB CSV dump arrives. You need answers today, not a loading pipeline. This is the single most common reason we reach for it.
Tests and CIA real analytical engine with no service to start in the test harness. Spin it up in memory, assert on the result, throw it away.
Agent and tool-calling workloadsAn agent that needs to answer questions over a dataset can be handed a DuckDB connection instead of warehouse credentials. No network, no quota, no cost per query, nothing to leak.
Querying object storage directlyWith httpfs, a Parquet lake on R2 or S3 becomes queryable without a query service in front of it. 2.0's async I/O is what makes this practical on an ordinary connection.
05 · SA context

Why this one lands particularly well locally.

Three South African constraints — FX exposure, data residency, and bandwidth — all push in DuckDB's favour.

No dollar line item. The warehousing conversation in South Africa usually stalls on the same thing: the tool is priced in dollars, billed monthly, and the rand moves. A client who approved a budget at one exchange rate is looking at a different number two quarters later, and nobody enjoys that meeting. DuckDB has no per-query cost, no per-seat cost and no subscription, so the analytical layer stops being an FX-exposed operating expense. The compute is whatever machine you were already paying for.

POPIA and data residency, simplified. Because DuckDB runs in your process, personal information does not leave the host it is already on. There is no vendor to assess as an operator, no cross-border transfer to justify under POPIA's section 72, and no data-processing agreement to negotiate. For analysis over personal information — HR data, patient records, debtor books — that is a materially shorter compliance path than sending the same data to a warehouse in another jurisdiction. The obligation that remains is the ordinary one: the host it runs on is still processing personal information and still needs the appropriate security safeguards.

Bandwidth is a real constraint, and columnar helps. Reading Parquet off object storage transfers only the columns and row groups a query touches. On a connection where moving a full dataset is slow or metered, that projection pushdown is not an optimisation detail — it is the difference between a workable pattern and an unworkable one. Pair it with an R2 bucket for zero egress fees and the data-movement cost of the whole arrangement approaches nothing.

Load shedding. An in-process database has no daemon to come back up and no connection pool to re-establish. A job that was interrupted is simply re-run. Keep the source data as files on durable storage and treat the .duckdb file as derived — rebuildable rather than precious — and an outage costs you one re-run rather than a recovery procedure.

06 · Gotchas

Things that only bite once you ship.

Most of these come from treating an in-process library as though it were a database server.

One writer. That's the whole concurrency model.

A DuckDB file permits a single process with write access at a time. Multiple readers are fine; two services both writing is not a configuration you can tune your way into. If more than one process needs to write, you need a database server — this is the single most common reason a DuckDB build has to be replaced later.

It is not a web application's database

No network listener, no users, no roles, no grants. The Quack protocol gives you a client-server option, but the engine's design centre is still one process doing analysis, not many clients doing concurrent reads and writes. Use PostgreSQL for the application and DuckDB for the analysis over its exports.

Memory is still finite

"Handles data larger than memory" is true — it spills to disk — but a query that spills runs at disk speed, not RAM speed. Set memory_limit and temp_directory explicitly in any job that runs unattended, or an oversized join will consume the host rather than fail politely.

The storage format is stable now, but check on upgrade

Backwards compatibility has been a commitment since 1.0 and 2.0 is an LTS line, which is a far better position than the pre-1.0 years when files did not survive upgrades. Still: pin the version in production jobs, and read the release notes before moving a persisted .duckdb file across a major version.

Extensions are a runtime dependency

INSTALL httpfs fetches from the internet on first use. In a locked-down container or an air-gapped environment that call fails at the worst moment. Bundle the extensions into the image, or use a build that ships them statically.

SQL that looks like Postgres isn't always Postgres

The dialect is close enough that most queries port directly, which is exactly why the differences surprise people. Window-function edge cases, type coercion and some date arithmetic behave differently. Test ported queries against known results rather than assuming equivalence.

07 · Decision guide

Use it for, skip it for.

DuckDB is an unusually easy yes inside its envelope and an unusually clear no outside it. The boundary is concurrency.

Use DuckDB when

  • The analytical work happens in one process — an ETL step, a notebook, a CLI tool, a scheduled job, a test.
  • The data is files: Parquet, CSV or JSON, locally or on R2 / S3 / GCS, and you'd rather query them than load them.
  • The dataset is bigger than pandas is comfortable with and smaller than a warehouse is worth — roughly single-digit GB to a few hundred GB.
  • Personal information must not leave the host, and you want the shortest POPIA path available.
  • You want no dollar-denominated subscription in the analytical layer.
  • An agent needs to answer questions over a dataset without being handed warehouse credentials.

Skip DuckDB when

  • More than one process needs to write. This is the hard boundary, not a tuning problem. Use PostgreSQL or ClickHouse.
  • It is backing an application — you need users, roles, grants and a network listener. That is PostgreSQL's job.
  • Many people need to hit the same dataset concurrently through a BI tool. ClickHouse is built for that shape; DuckDB is not.
  • The data genuinely runs to tens of terabytes with queries over all of it. At that point the specialist warehouses earn their cost.
  • You need streaming ingestion with sub-second freshness. DuckDB has no ingestion service to stream into.
  • Your organisation's policy requires a vendor with a support contract behind the analytical engine. A foundation-governed MIT project may not clear that bar, whatever its technical merits.
08 · 2ⁿ Perspective

How this leaf compounds in the tree.

DuckDB is the piece that lets an analytical layer exist before anyone has approved a warehouse. That changes the order you can do things in.

The usual sequence is: decide on a warehouse, provision it, build the pipeline, then finally find out what the data actually says. DuckDB inverts it. You can answer the analytical questions first — against the exports you already have — and only then decide whether any of it justifies a warehouse. A good share of the time it doesn't, and the honest outcome is a scheduled job writing Parquet with DuckDB doing the compute.

It also changes what you can hand an agent. A warehouse connection given to an agent is a standing credential against a billable service with a blast radius. A DuckDB file is a read-only artefact: no network, no quota, no cost per query, and nothing that leaks if the agent misbehaves. For the analytical half of agent work that is a far better-shaped primitive, and it is why this leaf sits upstream of the agent nodes as well as the data ones.
