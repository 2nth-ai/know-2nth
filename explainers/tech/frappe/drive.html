tech/frappe · Drive · Skill Leaf

Your files, your server,
and a beta warning.

Frappe Drive is open-source file storage, sharing and collaborative document editing built on the Frappe Framework — multi-part uploads, in-browser previews, video streaming, granular sharing, per-user quotas, and a real-time collaborative editor backed by CRDTs. It is also, in the maintainers' own words, in beta, with a standing instruction to keep backups and not to make it your only copy. That warning is the most useful thing on the project page and this leaf takes it seriously.

Live Frappe Framework app AGPL v3 Beta Vue 3 · TipTap · Yjs
01 · What it is

Google Drive's shape, on infrastructure you own.

Frappe Drive splits into two halves. Core is the file manager: large uploads handled as multi-part, whole-folder uploads that preserve structure, in-browser previews for supported types, video streamed from the server rather than downloaded whole, search across your files and files shared with you, and per-file activity logs showing permission and metadata changes over time. Sharing is granular — individual users, groups, everyone on the site, or published publicly — with guest users for controlled outside access. Storage can be pooled across all users or allocated as a per-user quota.

Writer is the document editor: real-time collaborative editing with users or guests, annotations that can be replied to and resolved as suggestions, manual versioning so you can pin a state to return to, automatic versioning underneath that, and .docx import.

Underneath it is Frappe Framework for the backend and permissions, Frappe UI (Vue) for the interface, TipTap over ProseMirror for the editor, and Yjs — a CRDT — for the real-time collaboration in both documents and annotations. The CRDT choice matters: concurrent edits merge without a central lock, which is what makes simultaneous editing feel like Google Docs rather than like a file share with a stale-copy problem.

Why this exists at all

Frappe Framework has had capable file handling since the beginning, and the maintainers say so plainly — the idea of a standalone Drive had been circulating internally since 2015. What pushed it from "the framework already does files" to a separate product was collaboration: previews, sharing semantics, guest access and co-editing are a different problem from attaching a document to a record. Worth knowing, because it tells you where the maturity is. The storage and sharing layer inherits a decade of framework work. The collaborative editor does not.

02 · The beta warning

Read this before you migrate anything.

Frappe Drive's own README carries two warnings, and they are not boilerplate. Taken together they say something specific about where this software currently is.

"Frappe Drive is in beta. It is strongly advised to take backups in production use."

Not "beta" in the sense of a stable product with a cautious label. The project is telling you it expects production users to need their backups.

"If you're self hosting Frappe Drive, do not use the app as the only way to store your files."

This is the sentence that should drive your architecture. A file store that must not be the only copy is, by definition, not yet a system of record. It is a collaboration surface in front of one.

What that means in practice

Do not run a client's only copy of their documents on a self-hosted Frappe Drive, and do not decommission whatever they are migrating from until you have restored from your own backup at least once and watched it work. Verified, tested, restore-rehearsed backups are the price of entry — and a backup you have never restored is a hypothesis, not a backup. If that operational commitment is not something the engagement can carry, the honest answer is either Frappe Cloud's managed hosting, where automated backups are part of what you are paying for, or a different product entirely. The maintainers make the same recommendation themselves, which is a good sign about the project and a clear signal about the self-hosted path.

03 · How it works

Installing it, and the dependencies people miss.

Drive needs system packages beyond the usual bench setup — the previews and video streaming are not pure Python.

# Bare metal, on an existing bench
bench get-app drive --branch main

# Drive-specific system packages — skip these and previews fail confusingly
sudo apt install ffmpeg libmagic       # Debian / Ubuntu
brew install libmagic ffmpeg           # macOS

bench install-app drive
bench start
# Production via the easy-install script
wget https://frappe.io/easy-install.py

python3 ./easy-install.py deploy \
    --project=drive_prod_setup \
    --email=you@example.co.za \
    --image=ghcr.io/frappe/drive \
    --version=stable \
    --app=drive \
    --sitename files.example.co.za

ffmpeg and libmagic are the whole preview story

These two packages are why the install instructions differ from every other Frappe app. libmagic does content-based file type detection — it reads what a file actually is rather than trusting its extension. ffmpeg handles video transcoding and thumbnailing for streaming. Miss them and Drive installs cleanly, accepts uploads, and then fails to preview or stream in a way that looks like a bug in the app rather than a missing system dependency. This is the single most common first-day support question on Drive, and it is a one-line fix.

04 · Gotchas

Where it gets tricky.

Storage growth is unlike anything else on the site

An ERPNext site's disk grows slowly and predictably. A file store grows at whatever rate your users upload, and video is the accelerant. Decide up front whether you are pooling storage across all users or setting per-user quotas — Drive supports both, and choosing neither means choosing "pooled and unbounded" by default. Monitor disk as a first-class alert, not an afterthought.

The default backup story does not cover the files

Frappe's standard backup takes the database and, depending on flags, the files directory. Confirm which you are actually taking, and confirm the restore path for a site whose file volume is measured in hundreds of gigabytes rather than megabytes. A database-only backup of a Drive site restores an intact index pointing at nothing.

Real-time collaboration needs WebSockets through your proxy

Yjs synchronises over a live connection. Behind a reverse proxy that has not been configured to pass WebSocket upgrades, the editor loads and then silently stops merging other people's changes — the worst possible failure mode for a collaborative editor, because two people can edit for an hour before anyone notices they are not seeing each other.

.docx import is import, not fidelity

Drive imports Word documents into its own editor. That is a content migration, not a format-preserving round-trip. Complex layouts, tracked changes, embedded objects and heavy styling will not survive intact. Set expectations before someone migrates a contract template library and discovers the formatting has been reinterpreted.

Guest access is a genuine external-sharing surface

Guest users and public publishing are useful and are also the two features most likely to leak. Anything a user can publish publicly, a user eventually will. Decide the policy deliberately, and audit published files periodically — the per-file activity log exists precisely so you can.

05 · Decision guide

Use it for, skip it for.

Use Frappe Drive when

  • You are already on Frappe and want file collaboration under the same users, permissions and API as the rest of the site.
  • Data residency is the driver — documents genuinely must sit on infrastructure in a jurisdiction you control.
  • You are running it on Frappe Cloud, where automated backups and support are part of the plan rather than your problem.
  • The workload is working documents and team collaboration, with a real system of record living somewhere else.
  • You want per-user storage quotas and audit trails on file permission changes without buying an enterprise content platform.

Skip Frappe Drive when

  • It would be the only copy of anything that matters. The maintainers say this themselves; believe them.
  • You need document management with retention policies, legal hold, records classification or e-discovery. That is an ECM problem, and Drive is not an ECM.
  • Microsoft 365 or Google Workspace is already paid for and deployed. You would be adding a second, less mature file store beside a working one.
  • Full Office format fidelity is required — round-tripping .docx with complex formatting and tracked changes intact.
  • Desktop sync clients matter. There is no equivalent of the OneDrive or Dropbox desktop agent; this is browser-first.
  • You cannot commit to tested, rehearsed backups. Under a beta warning this explicit, that is not a corner worth cutting.
06 · South African context

Where this lands in SA delivery.

POPIA · residency is the real argument, and it is a good one

For an organisation whose POPIA position turns on where documents physically live, a self-hosted file store on local infrastructure answers the cross-border question directly rather than through a processor's assurances. Drive's per-file activity log — permission and metadata changes over time — is also the kind of evidence an Information Officer can actually use when asked who had access to what and when. That is a stronger operational answer than most SaaS drives give you without an enterprise tier.

The caveat is the one this whole leaf turns on: residency is worth nothing if the data is not durable. A POPIA-clean file store that loses files has traded one failure for a worse one. Section 19 of POPIA requires appropriate measures to secure the integrity of personal information, not only its location — and integrity includes not losing it.

Bandwidth and load shedding are architectural inputs, not excuses

Video streaming and large multi-part uploads are exactly the traffic profile that hurts on constrained connections. If users are on mobile data or a thin branch link, an in-browser preview that streams is much kinder than a download — that is a genuine point in Drive's favour. But a server that is unreachable during an outage window is a file store your team cannot use, and a collaborative editor whose WebSocket drops mid-session is a support call. Hosting locally is a residency decision; make the availability decision separately and deliberately, with UPS and connectivity costed in.

The FX case is real but narrower than it looks

Per-seat Workspace or Microsoft 365 licensing is dollar-priced and moves with the rand. Replacing it with self-hosted storage does convert an FX-exposed subscription into local infrastructure cost. Be honest about what is not replaced, though: most organisations keep the mail, the calendar and the identity layer, so Drive displaces one component of a bundle rather than the bundle. Cost the delta, not the headline.
