tech/frappe · Frappe Cloud · Skill Leaf

Managed hosting
that is itself a Frappe app.

Frappe Cloud is the official hosting service for the Frappe stack. The platform underneath it is press — an open-source Frappe app, AGPL v3, that you can read and self-host. That matters more than it sounds: the deployment model it enforces is not bench update on a server, it is a build pipeline that turns a set of git commits into a Docker image. Understanding that is most of understanding Frappe Cloud.

Live Managed hosting AGPL v3 (press) Docker + Ansible
01 · What it is

The hosting layer, open-sourced.

Frappe Technologies originally ran customer sites on an internal platform built to host ERPNext and little else. Customers wanted custom apps, SSH, control over their own updates. Frappe Cloud is the rebuild that gives them that, and press is the application that runs it.

Press is a Frappe app like any other — doctypes, the same permission model, the same REST surface — which produces the slightly recursive result that the hosting control plane for the Frappe stack is itself a Frappe site. It is published under AGPL v3 and documented for local setup, so "what does the platform actually do when I click Deploy" is a readable question rather than a support ticket.

What you get as a customer: multi-tenant site hosting where each site can run its own app versions and update independently, a dashboard over apps, servers, sites, billing, backups and updates, granular team permissions, automated backups and monitoring, a marketplace for third-party apps with compatibility checks and payouts, and billing that runs on daily or monthly subscriptions with wallet credits.

Why the open source matters practically

Not for the usual ideological reason. It matters because the exit path is legible: the same software that hosts you is the software you could run yourself, and the artefact it produces is a Docker image built from your own repositories. Lock-in on Frappe Cloud is commercial convenience, not a proprietary runtime you cannot reproduce.

02 · The deploy model

Commits become images, images become benches.

This is the concept that trips up teams arriving from a self-managed bench. There is no in-place update. There is a build.

Doctype What it represents Notable fields
App ReleaseOne commit of one app, cloned and validated before it is allowed into a buildhash, author, message, source, status, invalid_release, invalidation_reason
Release GroupThe "bench group" — a named set of apps on a Frappe version, bound to servers, with shared bench and site configversion, apps, servers, common_site_config, bench_config, is_push_to_deploy_enabled
Deploy CandidateA build of a release group: the image, and every knob baked into itapps, dependencies, environment_variables, packages, gunicorn_threads_per_worker, use_app_cache

The chain runs one way. A commit lands and becomes an App Release, which is validated — an invalid release carries a reason and does not proceed. A Release Group pins which apps at which versions belong together. Deploying produces a Deploy Candidate: a built image carrying your apps, your Python and Node dependency versions, your OS packages, your environment variables, and worker tuning such as gunicorn_threads_per_worker. Sites then move onto the new bench.

Two consequences follow, and they are the whole operational difference. First, a deploy is reproducible and reversible in a way a live bench update never is — the image either built or it did not, and the previous one still exists. Second, anything that is not in the image is not in production. Environment variables, system packages and dependency pins are build inputs on the Deploy Candidate, not things you SSH in and add. Teams used to patching a running bench feel this as friction for about a week and as a safety net thereafter.

is_push_to_deploy_enabled on the release group is the automation switch: push to the tracked branch and the build-and-deploy chain runs without anyone opening the dashboard.

03 · What runs underneath

Four moving parts.

Press (Frappe Framework)

The control plane. Doctypes for servers, sites, benches, releases, billing and the marketplace, with the ordinary Frappe REST API over all of it. This is the part you are clicking.

Agent (Flask)

A small Flask application that runs on each managed server and gives Press a way to act on sites and benches. Press does not SSH around issuing commands; it talks to Agent. If you are reasoning about blast radius, this is the boundary worth knowing.

Docker

The packaging layer. A Deploy Candidate is an image; a bench is that image running. This is why dependency and environment changes are build-time concerns.

Ansible

Server provisioning and configuration. Press uses it to bring machines into a known state before they ever host a site.

On infrastructure, the Cluster doctype is explicit about which providers Press can drive: AWS EC2, OCI, Hetzner, DigitalOcean, Frappe's own compute, and a Generic option for machines it did not provision. Clusters carry a region and availability zone. That is the platform's capability surface, and it is worth separating from the commercial question of which regions Frappe Cloud actually sells today — the second is a pricing-page fact, not a repository fact.

04 · Pricing reality

The shape, not the number.

This leaf deliberately does not quote plan prices. Hosting prices move, and a stale rand-converted figure in a knowledge tree is worse than no figure — read the current plans on the Frappe Cloud site before you budget. What is stable enough to be worth writing down is the shape of the billing, which is visible in the platform itself.

  • Subscriptions run daily or monthly. Daily accrual is unusual in this market and it is genuinely useful: a test site that exists for nine days costs nine days, which makes spinning up throwaway environments cheap in a way monthly billing discourages.
  • Wallet credits sit in front of payment. You top up a balance that consumption draws down, rather than every resource carrying its own card transaction. For a South African buyer this is the lever that matters most — see below.
  • The marketplace bills through the same system. Third-party apps carry their own pricing and payouts run through Press. A paid app is another line on the same account, not a separate vendor relationship.
  • Servers and sites are separate cost objects. Shared-tenancy sites and dedicated servers are different products in the model. Moving from one to the other is a real migration decision, not a slider.

The comparison that actually decides it

Frappe Cloud versus a VPS you manage is not primarily a hosting-cost question, because a small VPS will usually look cheaper on the invoice. It is a question of who owns upgrades, backups, restores and the 2am failure. Price the alternative honestly: the VPS plus the hours someone bills to keep benches patched, plus the cost of the first restore that does not work. If your organisation has no one who wants that job, the managed price is the cheap option even when the invoice is larger.

05 · Decision guide

Use it for, skip it for.

Use Frappe Cloud when

  • You run ERPNext or custom Frappe apps and have no one whose job is bench maintenance.
  • You want reproducible deploys and painless rollback without building that pipeline yourself.
  • You run several sites — client environments, staging, demos — and daily billing makes short-lived ones cheap.
  • You want the official marketplace apps installed and billed in one place.
  • You want an exit that is technically real: the same platform is open source and the output is a Docker image.

Skip Frappe Cloud when

  • A binding contract or policy requires the data to be physically in South Africa and the regions on offer do not include one. Check before you design around it.
  • You need deep OS-level customisation on the host. The image-build model is the point, and fighting it is miserable.
  • You already have a competent platform team, existing Kubernetes or Docker infrastructure, and monitoring you trust. You are buying something you have.
  • Your workload is one small internal site with two users and no growth plan — a modest VPS with honest backups is a legitimate answer.
  • Dollar-denominated recurring spend is itself the blocker for the business, and a local rand-billed host wins on procurement grounds alone.
06 · South African context

FX, latency and what POPIA actually says.

POPIA does not ban offshore hosting. This is the single most common misunderstanding in local ERP procurement and it costs organisations real money in avoidable architecture. Section 72 permits transferring personal information outside the Republic where conditions are met — among them that the recipient is subject to a law or binding agreement upholding principles of reasonable processing substantially similar to POPIA. In practice that is a contractual exercise: know which jurisdiction the data sits in, have the operator agreement in place, and record the basis. It is work, not a prohibition. Treat a blanket "POPIA means it must be in South Africa" claim as a prompt to read section 72, and get your own legal sign-off rather than ours.

Latency is a design input, not a dealbreaker. ERPNext is a server-rendered application with chatty forms, and a European or Indian region adds noticeable round-trip time for a Johannesburg user doing heavy data entry all day. It is usually tolerable and occasionally not — the honest test is to put a real capturer on a real site in the actual region for a day before committing, rather than arguing about milliseconds.

FX exposure is structural. Dollar-priced hosting against rand revenue means your infrastructure line moves with a currency you do not control, and it moves against you in exactly the months the rest of the economy is difficult. The wallet-credit model gives you a partial lever that per-month card billing does not: topping up when the rate is favourable converts a floating exposure into a fixed one for that balance. It is not hedging in any serious sense, but for a small business it is the difference between a predictable cost and a surprise.

The procurement framing that works

Bring three numbers to the decision: the monthly managed price converted at a rate you are prepared to defend, the fully-loaded cost of the person who would otherwise maintain the bench, and the cost of a day of downtime for the operation. Most South African SMEs running ERPNext find the second number dominates and the argument ends there.
