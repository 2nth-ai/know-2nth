tech/frappe · Print Designer · Skill Leaf

Invoices you design,
not invoices you code.

Print Designer is a Frappe app that puts a visual canvas where Jinja templates used to be. Drag fields onto a page, bind them to the document and its linked documents, and publish a print format without writing HTML. The part most teams miss until production: it also replaces the PDF engine. Pick chrome as the generator and you get modern CSS and a headless Chromium process to run and size.

Live Frappe Framework app AGPL v3 v1.6.7 Frappe v15 / develop
01 · What it is

A canvas bolted onto the Print Format doctype.

Every Frappe site already has a print format builder. It is fine for a logo, an address block and a table of line items. The moment finance asks for a two-column remittance advice, a QR code for a payment reference, or a brochure-style quotation, you drop into a custom format and write Jinja and CSS by hand — and then you own that template forever.

Print Designer is Frappe Technologies' answer to that. It is a separate app (print_designer, AGPL v3, currently 1.6.7) that adds a drag-and-drop designer, a table editor, multi-page layouts, and a scripting escape hatch for custom data and custom HTML when the canvas runs out. Barcode and QR rendering come from its own Python dependencies — python-barcode and PyQRCode — rather than from anything you template yourself.

The architectural point worth holding on to is that it is not a parallel printing system. The app registers a doctype_js override on the standard Print Format doctype, so a Designer format is just a Print Format record with a different editing surface. Everything downstream that already knows how to print a Print Format — the print view, the POS screen, download_pdf, your own server-side calls — keeps working. You are changing how the format is authored, not where it lives.

What you actually install

A Frappe app with five Python dependencies (PyQRCode, pypng, python-barcode, websockets, distro) and Python 3.10 or newer. The websockets entry is the tell: it is there to talk to a browser, which is the subject of the next section.

02 · The part that surprises people

It swaps out your PDF engine.

Print Designer claims the framework's PDF hooks. Installing it changes how PDFs are produced, per format, and that is a capacity decision as much as a design one.

The app's hooks.py takes over pdf_generator, pdf_body_html, pdf_header_html, pdf_footer_html and get_print_format_template, and installs before_request and after_request handlers. On each request it reads a pdf_generator field off the Print Format record, falling back to wkhtmltopdf. Two values matter:

  • wkhtmltopdf — the historical Frappe path. An old WebKit. Fast, modest memory, and indifferent to most CSS written this decade: no flexbox or grid worth relying on.
  • chrome — headless Chromium, driven over the DevTools Protocol on a websocket. Modern CSS renders the way the designer previewed it, which is the entire reason the option exists.

Choosing chrome means you now run a browser on your application server. Print Designer looks for a bundled headless_shell binary in the bench folder (per-platform chrome-linux, chrome-mac, chrome-win paths), allows chromium_binary_path in site config if yours lives elsewhere, and allows chromium_websocket_url to point at a browser on another host — a path the source itself marks as not yet tested. Browser start-up has a ten-second default timeout.

03 · Capacity reality

One browser, one PDF at a time.

Read chromium_max_concurrent: 1 carefully, because it is the number that decides whether this app survives your month-end. The default configuration starts a single Chromium instance and permits one concurrent render through it. The source carries an explicit note that handling multiple Chromium instances per worker is still to be implemented.

For interactive printing — a user opens an invoice, clicks print, waits a second — that is entirely adequate and you will never notice. For a statement run that generates four thousand PDFs on the 1st of the month, you are serialising four thousand browser renders behind one connection, with a cold browser start if persistence is off. That is not a reason to avoid the app; it is a reason to decide, before you commit, which formats need chrome and which can stay on wkhtmltopdf.

The practical split

Set chrome on the handful of formats where layout is the product — customer-facing quotations, brochures, anything with a designed grid. Leave the high-volume internal paper — picking slips, delivery notes, bulk statements — on wkhtmltopdf. The pdf_generator field is per Print Format precisely so you can make that call format by format rather than site-wide. Raise chromium_max_concurrent only with memory headroom measured on your own box, and turn on persistent Chromium before you raise concurrency, not after.

04 · Gotchas

Things worth knowing first.

The version warning is behind the stack

The project README still states that Print Designer is compatible only with Frappe v15 and develop. Meanwhile the published ERPNext images have moved on — a version-16 line is shipping alongside version-15. If you are standing up a new site on v16, treat Print Designer compatibility as something to verify on a throwaway bench rather than assume, and check the repository's own branches before you plan the rollout.

Rendering is not guaranteed deterministic

The browser code carries a standing TODO to implement deterministic rendering via the DevTools Protocol, blocked on platform support. In practice: do not assume byte-identical PDFs across runs or across hosts. If you have a compliance or archival requirement that two renders of the same document must match exactly, test that specifically — the project has not claimed it.

AGPL v3, like the rest of the stack

Print Designer is AGPL v3, the same licence as the framework and ERPNext. Using it to print your own documents carries no obligation. Shipping a modified Print Designer as part of a hosted product you offer to others is where the network-use clause starts to matter, and that is a legal question, not a technical one.

You still own a template

The scripting escape hatch for custom data and custom HTML is genuinely useful and genuinely a trapdoor. A format with substantial custom script is a maintained artefact again — the thing the visual designer was meant to save you from. Worth noticing when it happens, rather than discovering it at handover.

05 · Decision guide

Use it for, skip it for.

Use Print Designer when

  • Your print formats are a recurring change request and a developer is in the loop every time.
  • Layout quality is customer-facing — quotations, proposals, branded statements that represent the organisation.
  • You need barcodes or payment QR codes on documents and would rather not template them yourself.
  • Finance or ops staff are capable of maintaining their own formats if you give them a canvas.
  • Volume is interactive rather than batch, or you can keep batch formats on the old generator.

Skip Print Designer when

  • Your bottleneck is bulk generation — thousands of documents in a window. One Chromium at concurrency 1 is the wrong shape for that, and tuning it is real work.
  • Your application server has no memory headroom. A browser process is not free, and small VPS instances feel it.
  • You need byte-reproducible output for archival or audit. That is an open TODO, not a feature.
  • You are on Frappe v16 and cannot afford to validate compatibility yourself yet.
  • Your existing Jinja formats work, nobody is asking for changes, and the only gain would be aesthetic. The standard builder plus one good custom format is a perfectly defensible end state.
06 · South African context

Documents, residency and the rand.

Two things make this leaf more than cosmetic for a South African organisation.

The first is cost shape. Print Designer is free; the Chromium process is not. If you are sizing a server in rands against dollar-priced hosting, "add a browser to the app server" is a line item, and the honest comparison is one slightly larger instance against a per-document SaaS document service. Deciding per format — chrome where it shows, wkhtmltopdf where it does not — is how you keep that instance small. For a business billing in rands, resisting an instance-size upgrade for formats nobody outside the warehouse ever sees is the whole game.

The second is POPIA. A print format is a personal-information processing surface: payslips, statements, delivery notes with names and addresses. Three habits follow. Keep generated PDFs inside the same site and permission model as the records they came from, rather than dropping them on a share with looser access — the designer does not change your permissions, but a careless export pipeline around it does. Treat a format that pulls from linked documents as a potential over-collection: the canvas makes it trivially easy to put a customer's full contact record on a document that only needed a delivery address. And if you point chromium_websocket_url at a browser on another host, note that document content now crosses to that host — worth knowing where it sits before you do it.

Who this suits here

SMEs already running ERPNext with an in-house finance person who keeps asking for layout changes. The win is removing the developer from that loop. Organisations printing at genuine volume — distribution, logistics, utilities — should scope the generator split before installing, not after.
