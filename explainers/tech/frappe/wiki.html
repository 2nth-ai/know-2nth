tech/frappe · Wiki · Skill Leaf

Documentation with
an approval trail.

Frappe Wiki stores pages as Markdown and refuses to let edits land unreviewed. Changes collect into a change request that diffs, reviews and approves like a pull request — so "who changed this procedure and who signed it off" is a query, not an investigation. Add GitHub sync, space-level roles, first-party analytics and a published llms.txt, and it is the one app in the suite built for documentation you have to defend.

Live Frappe Framework app MIT licence Markdown · Tiptap v3.x · Frappe v15/v16 GitHub sync
01 · What it is

A wiki with a review step.

Frappe Wiki is a wiki app for product guides, help centres, company handbooks and team notes. Writers get a rich text editor; readers get a page tree, a table of contents, search, PDF download and per-page feedback. Content is stored as Markdown, not as an opaque blob, which matters for everything downstream.

The feature that justifies choosing it over Notion or Confluence is the review model. Edits are not applied directly — they collect into a change request that behaves like a branch. A reviewer sees a diff, then approves, requests changes or rejects. Readers can propose changes too, without write access to the page. Under the hood that is a Wiki Page Patch document carrying raised_by, approved_by, a status and both versions of the content.

That single mechanism is what turns a wiki from a pile of documents into something you can point an auditor at. "Who changed this procedure, who approved it, and when" is a query against Wiki Page Patch, not an archaeology exercise in a page-history sidebar. Most wikis record that an edit happened. This one records that someone signed it off.

Built to be read by agents, on purpose

Every page is served with a Markdown copy, meta tags, social cards and a sitemap, and the space publishes an llms.txt index. There is also a skill that lets a coding agent draft change requests rather than edit pages directly — so an agent's contribution arrives in the review queue, with a human approving it, instead of silently landing in production documentation.

That is the right shape for agent-written docs, and it is the same pattern this site uses: know.2nth.ai publishes its own llms.txt and a Markdown rendering of every leaf for exactly this reason. Human-readable and agent-consumable from one source, with a person in the approval path.

03 · How it works

Markdown in the database, Git on the side.

Three things are worth understanding before you commit: the review flow, the GitHub sync, and the search and analytics engines, which are not what you would expect from a Frappe app.

The review flow as data. Because a change request is a document, the governance reporting you would otherwise ask someone to compile by hand is a filter.

# Change requests awaiting review — the editorial queue
GET /api/resource/Wiki Page Patch
  ?filters=[["status","=","Under Review"]]
  &fields=["name","wiki_page","raised_by","creation","message"]
  &order_by=creation asc

# Approval trail for one procedure — who signed off, and when
GET /api/resource/Wiki Page Patch
  ?filters=[["wiki_page","=","sop-stock-take"],["status","=","Approved"]]
  &fields=["raised_by","approved_by","modified","message"]
  &order_by=modified desc

GitHub Sync. A space can be kept in step with a folder of Markdown files in a GitHub repository, with a preview before pushing. Because pages are stored as Markdown, this is a genuine two-way mapping rather than a lossy export — which means developer documentation can live in the repo where developers already work while non-technical colleagues edit the same content in a browser. The connection is a GitHub App OAuth link held in Wiki GitHub Connection, and each run writes a Wiki Git Sync Log.

Search and analytics are not MariaDB. Full-text search runs on SQLite FTS5, and page-view analytics counts are served by DuckDB. This is unusual for a Frappe app and it is a deliberate trade: both are embedded engines, so you get real full-text search and fast aggregate counts without standing up Elasticsearch or a separate analytics service. The operational consequence is that there are now extra on-disk files that matter and that your Frappe backup story may not cover by default. Check that before you rely on it.

Version compatibility is explicit, which saves a bad afternoon: the master (v2.x) line runs on Frappe v15, version-3 (v3.x) runs on both v15 and v16, and develop is nightly and unstable. Frappe 13 and 14 are unsupported. For a new install on a v16 bench, version-3 is the branch you want.

04 · Gotchas

Where it gets tricky.

Install the right branch, deliberately

The app's branches map to Frappe versions and the default is not always what you want. Install version-3 explicitly for a v15 or v16 bench. Taking develop because it sounds current lands you on a nightly branch the project itself labels unstable.

The review flow needs someone to actually review

A change-request model with no reviewer is a queue, and a queue nobody works is worse than direct editing — contributors stop bothering. Name the reviewers per space before rollout and decide what the service level is. The mechanism cannot supply the editorial will.

Search and analytics add files to your backup scope

SQLite FTS5 and DuckDB mean search indexes and analytics counts live outside the MariaDB database your Frappe backups cover. Verify what your backup actually captures and whether a restore gives you a working search index or one you must rebuild.

Space permissions are role-based, not per-page ACLs

Access is granted per space via Wiki Space Role. That is clean and it is coarse. If your requirement is "this one page is visible to three named people", you are structuring spaces around permissions rather than around subject matter.

Reader feedback collects email addresses

Wiki Feedback has an email_id field and settings to ask for contact details. Switched on for a public help centre, that is a personal-information collection point with a lawful-basis and retention obligation attached. Decide that deliberately rather than by leaving a default on.

05 · Decision guide

Use it for, skip it for.

Use Frappe Wiki when

  • Documentation changes need an approval trail — SOPs, procedures, policies, anything an auditor or a certification body will ask about.
  • You want developer docs in Git and the same content editable in a browser by people who will never open a terminal.
  • You are already on Frappe and want the handbook on the same site, same users, same roles, no extra subscription.
  • You want agents to draft documentation into a review queue rather than write directly to published pages.
  • A public help centre with SEO metadata, sitemap, per-page feedback and first-party analytics is the deliverable.
  • MIT licensing matters — like Builder, this one is not AGPL.

Skip Frappe Wiki when

  • You need per-page or per-user access control. Space-level roles are the granularity on offer.
  • Your team wants the Notion or Confluence experience — databases, boards, embeds, deep third-party integrations. This is a wiki, and intentionally so.
  • Real-time collaborative editing on the same page is the requirement. The model here is propose-and-review, which is the opposite design choice.
  • Nobody will do the reviewing. Without reviewers the main advantage becomes friction and contribution dies.
  • You are not on Frappe and want a docs site. A static site generator deployed from a repo is simpler and cheaper to operate.
06 · South African context

Documented, approved procedure is the local requirement.

The approval trail is the reason this leaf is worth a South African delivery team's attention — it maps onto obligations that already exist.

Approved procedure, evidenced. A good deal of SA compliance work turns on showing that a documented procedure existed, that it was approved, and that staff had access to the current version. POPIA Section 19 expects documented security safeguards; the OHS Act expects documented safe working procedures; ISO certification and B-BBEE verification both ask for current, controlled documents. A wiki where every change carries a raised_by, an approved_by and a timestamp produces that evidence as a side effect of normal work, instead of as a scramble before an audit. That is a materially stronger position than a shared drive full of files named SOP_final_v3_REVISED.

What it does not do. It is a document-control mechanism, not a compliance product. There is no ISO 9001 template pack, no review-due-date scheduling, no mandatory read-and-acknowledge tracking — if you need to prove a specific employee read a specific version of a policy, that is build work against the API, or it belongs in Frappe Learning where completion is already tracked per learner. Pair the two rather than stretching either.

Residency and cost. Self-hosted on an SA region keeps policy documents, contributor identities and reader feedback in-country, which keeps the cross-border section of a POPIA assessment short. On cost, the comparison is the familiar one: Confluence and Notion bill per user per month in dollars, so the bill for a growing organisation rises in rand on FX alone. Self-hosted, the cost is infrastructure plus the person who maintains it. The caveat is also the familiar one — that person has to exist, and for documentation specifically the harder scarcity is usually not hosting but an owner who keeps the content true.
