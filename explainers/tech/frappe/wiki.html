tech/frappe · Wiki · Skill Leaf

Markdown docs with
an approval queue.

Frappe Wiki is a deliberately small documentation app: markdown authoring, revision history, an optional change-approval workflow, attachments, an auto-generated table of contents, and RediSearch-backed search. Frappe wrote it because they needed somewhere to put the ERPNext manual and did not like the alternatives. It is MIT licensed — unlike most of the ecosystem around it — and it publishes new pages and edits without a redeploy.

01 · What it is

A wiki that knows what it isn't.

Frappe Wiki is an open-source wiki app on the Frappe Framework, suited to dynamic, text-heavy content: documentation, knowledge bases, user manuals, company policies. Pages are authored in markdown. Small changes and whole new pages publish on the fly with no downtime and no build step. Revision history is kept, and a change-approval mechanism lets you review edits before they go live.

The origin is the usual Frappe story and it explains the scope: they wanted a simple, clean, open-source wiki to write the ERPNext documentation, could not find a good option, and wrote their own. It is now what they use internally for manuals and policies. The design goal was a delightful experience for writers and readers — not feature coverage against Confluence.

That restraint is the thing to evaluate. The feature list is short by intent: create and organise pages, author in markdown, set up controlled updates with a review-and-approve workflow, attach files, get an automatic table of contents, and extend behaviour with custom scripts configured in Wiki Settings. If your requirement is on that list, it is a good fit. If your requirement is off it, there is no plugin that will put it on.

MIT licensed — worth checking, worth noting

Frappe Wiki ships under MIT, as does Frappe Builder. Raven, Drive, LMS and Print Designer are AGPL v3. If you plan to fork this into a client-facing product, that distinction decides the conversation — and it is a good reminder that "the Frappe ecosystem" is not one licence. Read the licence file in each repository.

02 · Under the hood

Three dependencies, one of them operationally significant.

ComponentRoleWhat to watch
Frappe FrameworkBackend, users, permissions, REST API, the page routes themselvesWiki pages are doctypes. That is what makes the API and the permission model free.
Ace EditorThe in-browser markdown editing surfaceA code editor, not a WYSIWYG. Writers who expect Notion will feel the difference on day one.
RediSearchSearch and indexing, on top of RedisThe one that bites. RediSearch is a Redis module, not core Redis.

Check your Redis before you promise search

Search depends on the RediSearch module being available in whatever Redis your bench talks to. A self-managed Redis you build yourself is fine — install the module. A managed Redis from a cloud provider frequently is not: managed offerings ship a curated module list, and RediSearch is not universally on it. Verify this against your provider's documentation before you design around search, because discovering it after migration means either re-hosting Redis or shipping a wiki nobody can search. It is a five-minute check and a two-day problem.

03 · The structural trade

Database-resident docs, not docs-as-code.

This is the decision that actually separates Frappe Wiki from the alternatives, and it has nothing to do with features.

Wiki content lives in the database as doctype records. Docusaurus, MkDocs, Starlight and the rest keep content as markdown files in a git repository. Both are markdown; they are not the same product.

Database-resident means: publish instantly with no build and no deploy, edit from a browser without a local toolchain, use Frappe's roles to decide who can write what, and get an approval workflow as a built-in rather than as a pull request. Non-technical staff can maintain the company policy pages without anyone explaining a branch.

Docs-as-code means: diffs, code review, docs versioned alongside the code they describe, CI that can lint links and build a preview per branch, and content you can grep, script over, and move to a different tool in an afternoon.

Pick on who writes. If it is engineers documenting a system they also commit to, docs-as-code wins and it is not close. If it is a mixed group — support, HR, operations — maintaining policies and manuals, the browser-editable, approval-gated wiki wins for the same reason. Frappe Wiki's revision history and change approval exist precisely because that second group needs guardrails the first group gets from git.

The migration question is the honest one

Content in a database is content you have to write an exporter for. Before committing a large documentation estate to any database-resident wiki — this one included — confirm you can get the markdown back out in bulk. The Frappe REST API makes that straightforward, so this is a "write the script once" problem rather than a lock-in problem, but it is only straightforward if you check before you have four hundred pages rather than after.

04 · Gotchas

Where it gets tricky.

The editor is a code editor

Ace gives you markdown source, not a rich-text surface. Engineers will not notice. An HR manager updating a leave policy will, and "just learn markdown" is a rollout plan that fails quietly — people stop updating the page instead of complaining about the editor. Budget a short internal guide, or accept that a small group will do the editing.

Approval workflow is a policy decision, not a switch

Controlled updates are a feature, and an unstaffed review queue is worse than no review queue: edits sit unpublished, contributors give up, and the wiki rots while looking governed. Turn it on only where the content genuinely warrants it — policies, customer-facing docs — and name the reviewer.

Custom scripts in Wiki Settings are a shared surface

Wiki Settings supports custom scripts to extend behaviour. That is genuinely useful and it is site-wide configuration executing on your documentation pages. Treat it with the same care as any other code path: know who can edit it, know what it does, and do not let it become the place where three undocumented hacks live.

Permissions on a public wiki need deliberate thought

A Frappe site can serve wiki pages publicly. The moment it does, what the Guest role can read is a publishing decision, and internal pages on the same site are one misconfigured permission away from being indexed. Separate public documentation from internal knowledge by role, and verify it from a logged-out browser rather than from the admin account.

Diagrams, embeds and rich media are not the strength

Markdown plus attachments covers text and files well. Sequence diagrams, embedded dashboards, interactive content — anything Notion or Confluence users take for granted — is not what this app is for. Check your actual content against that before migrating.

05 · Decision guide

Use it for, skip it for.

Use Frappe Wiki when

  • You already run a Frappe bench and want documentation under the same users, roles, and audit trail.
  • Non-technical staff need to maintain pages from a browser without a git workflow.
  • Policies or customer-facing documentation genuinely need a review-and-approve step before publishing.
  • You want to stop paying per-seat for Confluence or Notion for content that is mostly text.
  • MIT licensing matters because you plan to fork or embed it.
  • Instant publishing without a build pipeline is worth more to you than diffs and branch previews.

Skip Frappe Wiki when

  • Engineers are the writers and the docs describe code. Docs-as-code with MkDocs, Docusaurus or Starlight is the better tool and it is not close.
  • Your managed Redis cannot run the RediSearch module and you are unwilling to re-host Redis. Search is not optional in a wiki.
  • You need Notion or Confluence affordances — databases, embeds, inline comments, rich media, templates as a first-class concept.
  • You are not on Frappe. This is not a reason to stand up a bench.
  • You need multi-space permissions and per-space administration across many independent teams.
  • Your documentation must be versioned alongside product releases — v1 docs and v2 docs living side by side is a docs-as-code pattern.
06 · South African context

Where Wiki fits SA delivery.

The compliance-documentation use case is the strong one

SA organisations carry a standing documentation burden: POPIA processing records and retention schedules, B-BBEE evidence, health-and-safety procedures, employment equity plans, ISO or industry procedure manuals. All of it is text, all of it needs revision history, and much of it needs a named approver before publication. That is Frappe Wiki's exact feature set, and it is a more honest fit than "we need a Confluence replacement". Keeping it on the same bench as Frappe HR means the policy and the employee it applies to share a permission model.

POPIA · documentation is not automatically low-risk

A wiki looks like it holds procedures, and then someone pastes a worked example with a real ID number in it, or a customer escalation write-up with a name attached. Self-hosting in an SA region keeps that in-country, which is the easy part. The harder part is the review habit: personal information in documentation is still personal information, and it is the category most likely to be missed in a data inventory precisely because nobody thinks of the wiki as a data store.

FX · small, real, and not the main reason

Per-seat documentation tools are USD-billed and price by headcount, including the occasional reader who edits twice a year. A self-hosted wiki on a bench you already run costs marginal infrastructure in rand. It is a genuine saving and it is rarely large enough to justify the migration on its own — the residency and single-permission-model arguments are the ones that carry the decision. Do not oversell the cost line to a client who will then measure you against it.
