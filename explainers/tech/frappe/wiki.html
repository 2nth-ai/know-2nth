tech/frappe · Wiki · Skill Leaf

Documentation with
a review step.

Frappe Wiki is an open-source wiki app on the Frappe Framework, built for product guides, help centres, company handbooks and team notes. Its distinguishing feature is not the editor — it is the change request. Edits collect like a branch, a reviewer reads the diff, and the page goes live on merge. Content is stored as Markdown, and the app ships a GitHub sync and an llms.txt index.

01 · What it is

A wiki that treats docs like code.

Frappe Wiki came out of Frappe’s own need: they wanted a clean open-source wiki for the ERPNext documentation, did not find one they liked, and wrote it. It now carries their user manuals and company policies. That origin shows in the design — it is built by people whose main problem was keeping a large, multi-author documentation set accurate, not by people building a note-taking app.

Writers work in a rich text editor. Readers get fast published pages with a page tree, a table of contents, search, light and dark mode and a PDF download. Content is stored as Markdown, which matters more than it sounds: it means the source is portable, diffable and syncable, and it is why the GitHub integration and the AI surface in section 03 are possible at all.

The organising unit is the space. A space holds the pages of one wiki — a product guide, a handbook — with its own URL, logo and access rules. A space can be public, or private to specific roles. One site can carry several.

The change request is the actual product decision

Most wikis optimise for frictionless editing: click, type, saved, live. Frappe Wiki deliberately does not. Your edits collect into a change request, a reviewer reads the diff side by side, and then approves, requests changes or rejects. Readers can propose changes too. If you have ever maintained documentation that quietly drifted wrong because anyone could edit anything instantly, you will recognise why someone built this. If you want a scratchpad, you will find it tedious. Both reactions are correct — they are just about different jobs.

03 · The agent surface

Why the llms.txt line matters.

Buried in the feature list is something worth pulling out, because it is the same bet this site makes. Frappe Wiki publishes a Markdown rendering of every page, a sitemap, and an llms.txt index — the emerging convention for telling an AI client what a site contains and where to find it. And it ships a skill that lets AI coding agents draft pages through the change-request flow, rather than writing straight to live content.

That second detail is the interesting one. The obvious way to let an agent maintain documentation is to give it write access. The better way is to give it the same constrained path a human contributor gets: propose, diff, human review, merge. The review step that makes the wiki slightly annoying for humans is exactly what makes it safe to point an agent at.

know.2nth.ai runs the same pattern from the other side — a generated llms.txt, a Markdown rendering of every leaf, and an MCP server over the tree. If you are building internal documentation that agents will consume as well as people, this is the shape to copy.

A caution on the AI drafting path

An agent that drafts through change requests is still an agent writing your documentation. The review step bounds the damage; it does not remove the need to read what arrives. Treat agent-drafted pages as submissions from a fast, confident contributor who has never been held accountable for being wrong — which is to say, review them properly.

Two embedded engines you did not ask for

Search runs on SQLite FTS5 and analytics on DuckDB, both embedded alongside your main Frappe database. This is a sensible engineering choice — both are excellent at exactly these jobs and neither needs a server — but it does mean your documentation app has three storage engines in it. Know that before you debug a search index at month end. If DuckDB is new to you, the tree has a warehousing branch.

05 · Gotchas

Where it gets tricky.

Two stable major lines, and they are not interchangeable

v2.x runs on Frappe v15 only; v3.x runs on v15 and v16. Both are marked stable, which is unusual and means the choice is yours to make deliberately rather than by default. If you are starting now on v16, you are on v3.x. If you are on a v15 site you intend to upgrade, starting on v3.x saves you a migration later.

The review workflow is the feature and the friction

Change requests are why this app exists. They also mean that fixing a typo is a proposal, a review and a merge. For maintained documentation that is correct. For a team wiki where five people want to dump meeting notes, it will feel like bureaucracy and people will route around it — usually into a chat channel where the information then dies.

MIT, which is the exception here

Frappe Wiki is MIT licensed. Most of the Frappe estate — Raven, Drive, Learning, ERPNext itself — is AGPL v3. If you are assembling a stack and reasoning about licence obligations, do not assume uniformity across apps from the same vendor. Check each one.

GitHub Sync is a sync, so decide which side wins

Keeping a space in step with a repository folder is powerful and it creates two places where the same content can change. Settle the direction of truth before you turn it on, and use the documented development-site preview rather than discovering the merge semantics in production.

06 · Decision guide

Use it for, skip it for.

Use it when

  • Documentation needs to be reviewed before it goes live — product guides, help centres, policies
  • You want the source in Markdown you can sync to Git rather than locked in a proprietary editor
  • You are already running Frappe and would rather add a space than add a vendor
  • Agents will read your documentation, and you want llms.txt and per-page Markdown without building it
  • You want per-space access control — a public product guide and a private internal handbook on one site
  • You need page-level analytics to find out which documentation anyone actually reads

Skip it when

  • You want a frictionless team scratchpad — the review step will be routed around
  • You are not running Frappe and would be standing up a site solely for a wiki
  • Your documentation is already in a Git-backed static site generator that works; this is a lateral move
  • You need real-time co-editing in the document itself — that is Frappe Drive’s Writer, not this
  • You need a specific compliance certification for your documentation platform that self-hosting will not produce
07 · South African context

What this changes for SA delivery.

POPIA — handbooks and policies are personal-information-adjacent

Company handbooks, HR policies, disciplinary procedures and client-specific runbooks carry more personal and confidential information than teams usually credit. Self-hosting puts that content in a database you control, in a region you chose, under your own role-based access rules — which for an SA organisation is a cleaner answer to “where does our policy documentation live” than a US-hosted knowledge base with a processing agreement attached.

The client-documentation angle for consultancies

If you deliver systems to SA clients, the handover documentation is part of the deliverable and sometimes part of the contract. Spaces with per-role access let you run one wiki with a public implementation guide and private client-specific sections, and the change-request flow gives you a defensible record of who approved what documentation and when. That is useful when a dispute turns on what the client was told.

FX — modest, but real at team scale

Hosted documentation platforms price per editor in dollars. A wiki on a Frappe site you already run does not, and documentation tools have a habit of accumulating seats — everyone needs to edit something eventually. The saving is smaller than on chat or storage because editor counts are smaller, so be honest: this is a consolidation and control decision first, and a cost decision second.
