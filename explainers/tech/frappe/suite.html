Seven products,
and no release yet.

Frappe Suite folds Drive, Writer, Sheets, Slides, Meet, Mail and Calendar into a single Frappe app. It is the successor to standalone Frappe Drive, which is now archived. The technology underneath is sound — Yjs, mediasoup, S3-compatible storage, JMAP. The version number is 0.0.1 and there are no release tags, so this leaf is a map of where things are going, not a deployment guide.

01 · What it is

Seven products, one app, version 0.0.1.

The successor to standalone Frappe Drive, Writer, Sheets, Slides, Meet, Mail and Calendar — and currently pre-release.

Frappe Suite is the consolidation of seven separate collaboration apps into a single Frappe app: Drive (files), Writer (documents), Sheets (spreadsheets), Slides (decks), Meet (video), Mail (email) and Calendar. It is the Frappe ecosystem's answer to Google Workspace, and it is the reason the standalone apps you may have been tracking have stopped moving.

This leaf exists in place of a Frappe Drive leaf, and the reason is the important part: frappe/drive is archived. Its README now says so in the first line and points here. If you were planning a deployment around standalone Frappe Drive, that plan needs revisiting — not because Drive stopped working, but because development moved and the standalone repo is no longer where it happens.

The blunt status check, and the thing to hold onto before reading anything else: the Suite repository reports version 0.0.1 and carries no release tags at all. Everything below is a description of something early, licensed AGPL v3, that is being built in the open.

Read this before you plan anything

Standalone Drive is archived, and its replacement has not cut a first release. That combination means there is currently no version of self-hosted Frappe file storage that is both actively developed and tagged as released. If you need production file storage this quarter, that is a reason to look elsewhere and revisit Suite later — not a reason to run 0.0.1 and hope. The honest recommendation for anything load-bearing right now is Nextcloud or object storage with a front end, and a calendar reminder to check back.

The technology choices are reassuringly unexciting, which in this category is the right instinct. 03 · Mail is not what you think

Suite does not run a mail server.

It is a very good mail client in front of someone else's Stalwart cluster, and the administration lives in a second app.

This is the single most misunderstood thing about Suite, and it is stated plainly in the project's own README: Suite does not run or administer a mail server itself. The servers are Stalwart clusters managed by a separate app, suite_cloud, and a Suite site is one tenant of a cluster.

The split is clean once you see it. End users read and send mail directly against the cluster over JMAP, using an app password minted per account — Suite only needs the cluster's URL for that. Every administrative change, though — domains, accounts, passwords, groups, mailing lists — goes through Suite Cloud's site API, which verifies the site actually owns what it is touching and then pushes the change to the cluster. The site never holds cluster admin credentials, which is a genuinely good security decision.

The consequence is what matters for planning. Mail and Calendar are fully usable with nothing but a JMAP server_url — anyone who already has an account can use the mailbox. But the Admin Dashboard, account creation and signup all require Suite Cloud: without it the dashboard is hidden from admins, its routes redirect back to the mailbox, and every endpoint in the admin API refuses. So you can run Mail without Suite Cloud, you just cannot administer it.

# Five connection values a Suite site carries.
# Frappe Cloud writes these into site_config.json when it registers
# the site; on a self-managed site the settings UI overrides them.

# Mail Settings — or the "mail" key of site_config.json

# Suite Settings — or top-level keys of the same name
suite_cloud_url

# Read through get_suite_cloud_config in suite/suite_core/utils.py.
# "Validate Suite Cloud Credentials" on Suite Settings confirms them.

If you deployed servers through Suite before the split

Sites that deployed mail servers through Suite before Suite Cloud was separated out keep their data. The path is: update Suite, run bench --site yoursite migrate, then bench --site yoursite install-app suite_cloud.

04 · Migrating from the standalone apps

The step that deletes your data.

Suite and the standalone apps cannot coexist, and uninstalling the old ones destroys their data.

Suite ships the same modules and doctypes as the standalone apps, so it cannot be installed alongside any of them — installation aborts and lists the conflicting apps. Getting from standalone Drive or Mail to Suite therefore means removing the old apps first, and this is where it gets genuinely dangerous.

Read the second step carefully: uninstalling a standalone app deletes that app's data on the site. The project's own documentation says so, and says that is precisely why the backup comes first. The migration works because Suite reuses the same tables, so a restored backup is picked up as-is — but the sequence passes through a state where your files and documents are gone from the site and exist only in the backup you took.

# 1. Back up the site WITH files. This is not optional.
bench --site yoursite backup --with-files

# 2. Uninstall every standalone app present.
#    THIS DELETES EACH APP'S DATA ON THE SITE.
bench --site yoursite uninstall-app drive
bench --site yoursite uninstall-app writer
bench --site yoursite uninstall-app sheets
bench --site yoursite uninstall-app slides
bench --site yoursite uninstall-app meet
bench --site yoursite uninstall-app mail
bench --site yoursite uninstall-app calendar_app

# 3. Install Suite, then 4. restore the backup.
#    Suite uses the same tables, so data is picked up as-is.

Rehearse this, do not perform it

Verify the backup restores onto a scratch site before you uninstall anything on the real one. A backup you have not restored is a hypothesis. On Frappe Cloud the same sequence runs through the dashboard — download from Backups, remove the apps on the Apps tab, install Suite, then restore — which makes it feel safer than it is. The deletion is just as real.

05 · Gotchas

Where it gets tricky.

Version 0.0.1, no release tags

The repository reports 0.0.1 and has cut no tagged release. There is no stable version to pin, no changelog to read between upgrades, and no signal yet about what the maintainers consider breaking. Treat develop as what it is.

Mail administration needs a second app and a cluster

Suite Cloud is a separate install, and behind it is a Stalwart cluster somebody has to operate. If you assumed self-hosting Suite meant self-hosting your email end to end, it does not — not without also running Stalwart and Suite Cloud yourself, which is a materially bigger undertaking than installing a Frappe app.

The seven products are not equally mature

They arrived as seven separate projects at seven different stages, and consolidation does not level that. Drive has the longest history; Slides and Meet are the newest surfaces. Evaluate the module you actually need rather than the suite as a brand.

Media processing is a real infrastructure dependency

Drive wants ffmpeg for video thumbnails and transcoding, and Meet runs a mediasoup SFU. Those are not pip installs you forget about — transcoding is CPU-hungry and an SFU needs predictable bandwidth and open UDP. Size the host accordingly, or video will be the thing that falls over.

Collaborative editing adds a server to operate

Realtime spreadsheets run through a Hocuspocus collaboration server. That is another process to supervise, monitor and upgrade, and when it is unhealthy the symptom users report is "the spreadsheet stopped saving" rather than anything that points at the cause.

Consolidation means a bigger blast radius

One app now carries files, documents, spreadsheets, decks, video, mail and calendar. A bad upgrade no longer takes out one capability. Staging stops being good practice and becomes the minimum.

06 · Decision guide

Use it for, skip it for.

Consider Frappe Suite when

  • You are evaluating rather than deploying, and want to know where the Frappe collaboration story is going.
  • You already run Frappe, want files and documents beside your business data, and can tolerate pre-release software on a non-critical workload.
  • You want a good JMAP mail client and already have (or will run) a Stalwart cluster plus Suite Cloud.
  • Object storage is your preference for files — Drive's S3-compatible backend means local SA object storage works.
  • You are contributing. It is AGPL v3, built in the open, and early is when contributions shape a project.

Skip Frappe Suite when

  • You need production file storage now. There is no released version, and archived standalone Drive is not the answer either — take Nextcloud or object storage with a front end.
  • You thought this meant self-hosted email end to end. Mail administration needs Suite Cloud and a Stalwart cluster you operate.
  • You are replacing Google Workspace or Microsoft 365 for a business that cannot absorb disruption. Not yet, and not close.
  • You cannot rehearse the standalone-app migration on a scratch site. The uninstall step deletes data.
  • Your ops capacity is thin. This is an ffmpeg pipeline, a WebRTC SFU and a collaboration server, not one more Frappe app.
07 · South African context

Where this lands in SA delivery.

The appeal is obvious and the timing is wrong, and it is worth being precise about both.

The appeal: Google Workspace and Microsoft 365 are dollar-priced per seat per month, which for an SA organisation is a rand cost that drifts upward with the exchange rate and never comes back down. A self-hosted suite converts that into infrastructure you can pay for locally. On top of that, POPIA makes the location of documents, email and calendars a question worth having an answer to — and "on a server in Johannesburg" is a much easier answer than a Section 72 cross-border assessment of a hyperscaler's data-processing addendum. Drive's S3-compatible backend means SA object storage is a supported target rather than a workaround.

The timing: none of that is a reason to put a business on 0.0.1. The organisations for which the FX and residency case is strongest are usually the ones least able to absorb a collaboration outage, and pre-release software is where outages come from. The suite that saves you dollars is worth nothing if finance cannot open a spreadsheet.

The sensible SA posture right now is to treat Suite as a watch item with a real review date. If the residency argument is pressing today, solve it with something released — Nextcloud for files, a hosted SA mail provider for email — and keep an eye on Suite's first tagged release as the signal that the calculation has changed. And when Mail does become viable, cost the Stalwart cluster and Suite Cloud honestly: self-hosted email is a real operational commitment, and SA deliverability problems are nobody's favourite Friday.
