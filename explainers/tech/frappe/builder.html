Frappe Builder is a visual, low-code website builder that publishes routes on your own Frappe site. 01 · What it is

A visual page builder that publishes to your own site.

Frappe Builder is a low-code website builder: you drag blocks onto a canvas in a Figma-like editor, bind them to data already in your Frappe site, and publish with one click. The output is a route on your own domain, served by your own Frappe instance — not a page hosted by a builder vendor.

The pitch that distinguishes it from Webflow or Framer is the data binding. A Frappe site already holds your products, your team, your job openings, your case studies as doctypes. Builder lets a page read those directly, including dynamic detail routes — one template that renders every product — without a headless CMS, an API layer, or a build step in between.

The credibility check most tools cannot offer: frappe.io itself is built on Frappe Builder. That is not marketing copy from the README so much as a load-bearing commitment — the vendor's own primary web presence is the test case.

The licence is the quiet headline

Frappe Builder is MIT. Almost everything else in the Frappe ecosystem — ERPNext, Raven, Frappe Learning, Frappe Suite — is AGPL v3. For an agency, that difference is commercial, not academic: AGPL's network-copyleft provision is a conversation you have to have with a client's legal team when you modify and host the software for them. MIT is not that conversation. If you build client websites for a living, Builder is the one piece of this stack you can fork, white-label and ship without a licensing discussion.

02 · How it works

Blocks, routes, and real doctypes.

Pages are documents. Data binding is server-side. Published output carries no builder runtime.

A Builder Page is a document holding a block tree, a route, and a publish state. Blocks are the visual primitives; components are reusable block groups; the theme carries your tokens. Because the page is a document, it versions, permissions and backs up exactly like an invoice does.

Data gets in three ways, in increasing order of power. A page data script runs server-side and returns the context a page renders against. Client scripts attach behaviour in the browser, globally or per page. Per-block data scripts and typed block props let an individual block compute its own values, and any property or style can be bound to a dynamic expression sourced from page data, a script, or a query parameter.

The performance claim is unusually specific for this category and worth repeating because it is checkable: Builder does not inject a framework runtime into published pages, which is why they score well on Lighthouse. Most visual builders ship their own JavaScript to every visitor. This one ships markup and your own scripts.

03 · Bob, the AI site builder

Grounded in your site, not guessing.

Builder ships an agent called Bob that edits pages conversationally. What makes it worth more than a novelty is the grounding: per the project's own description, Bob reads your existing pages and follows their design language by default, reuses your components and theme tokens, fits new pages into your route structure including dynamic detail routes, and wires forms and data-driven sections to real doctypes rather than inventing placeholder content.

The guardrails are explicit, and they are the right three. Bob's reads respect the acting user's permissions, so it cannot surface data that user could not already see. Sensitive changes wait for approval rather than applying themselves. And every AI edit is revertable — which, combined with Builder Snapshot, means the failure mode is an undo rather than a restore from backup.

The architecture underneath is the interesting part for anyone already running an LLM gateway. Builder AI Provider carries a litellm_provider field alongside api_base and api_key, which means model access is routed through LiteLLM's provider abstraction rather than hardcoded to one vendor. You point it at your own endpoint, your own key, and your own choice of model — and Builder AI Model records per-model vision support and token ceilings so the editor knows what it is talking to.

What this means for data residency

Because the provider is yours to configure, Bob is one of the few AI features in this ecosystem where you genuinely control where inference happens. Point it at a model in a region you are comfortable with — or at a self-hosted endpoint — and the cross-border question largely goes away. That is a meaningfully better posture than a feature wired to a single vendor's API, and worth checking against the POPIA position you have already taken for the rest of the stack.

04 · Gotchas

Where it gets tricky.

It is a page builder, not a design tool

The editor is Figma-like, which is not the same as Figma. There is no component variant system of real depth, no auto-layout equivalence, and no designer handoff workflow. Designers used to Figma will find it constraining; the tool is aimed at getting a designed page onto a live route, not at doing the design.

Pages couple to your doctypes

Data binding is the feature and also the lock-in. A page wired to Item and Website Item is a page that only makes sense on a Frappe site. There is no meaningful export path to static HTML or another CMS, so treat Builder pages as part of the application, not as portable content.

Dynamic routes need thought up front

Dynamic detail routes are powerful and easy to get subtly wrong — route collisions, missing canonical URLs, and pages that render for unpublished or permission-restricted records. Set canonical_url deliberately and test what an anonymous visitor sees, not just what you see as Administrator.

Analytics is a counter, not an analytics product

The built-in dashboard gives page views, unique visitors and top referrers off Builder Page Click. That is genuinely useful and genuinely minimal. No funnels, no segments, no attribution, no consent management — if marketing needs any of that, you are still installing something else, and that something else brings its own POPIA consent obligations.

Scripting escapes the no-code promise fast

The moment a page needs real logic you are writing page data scripts, client scripts and per-block data scripts. That is a strength — the escape hatch exists — but it means a Builder site can accumulate script in several places with no central view of it. Decide where logic lives before three people have each chosen differently.

Bob is only as safe as the provider you point it at

The permission and approval guardrails are real, but they govern Bob's access to your site, not what your chosen model provider does with the prompt. Page content, component names and bound field names go to whatever endpoint you configured. Choose that endpoint as deliberately as you would any other processor.

05 · Decision guide

Use it for, skip it for.

Use Frappe Builder when

  • You already run a Frappe site and need marketing pages, a customer portal or a careers page that reads live data from it.
  • You want one template to render many records — products, listings, team members — without building a headless CMS.
  • Page-load performance matters and you do not want a builder's runtime shipped to every visitor.
  • You are an agency: MIT licensing lets you fork, white-label and host for clients without an AGPL conversation.
  • You want an AI editing surface whose model provider you choose and control, rather than one wired to a single vendor.

Skip Frappe Builder when

  • You are not on Frappe. The data binding is the entire value proposition and it does not travel.
  • Your site is content-heavy editorial work. This is not a CMS for a newsroom — use a CMS.
  • You need a mature designer workflow, a design-token pipeline from Figma, or real component variants.
  • Marketing owns the site and needs A/B testing, personalisation, consent management and attribution out of the box.
  • You need the page content to be portable to another platform later. Plan for a rebuild, not an export.
  • Your team has no Frappe capability at all. The editor is approachable; debugging a dynamic route on a Frappe site is not.
06 · South African context

Where this lands in SA delivery.

For SA agencies and in-house teams, the honest comparison is against Webflow and WordPress, and Builder wins or loses on a narrow question: does the site need to show live business data?

If it does, Builder is unusually well placed. A distributor who wants a public catalogue backed by real ERPNext stock levels, a recruiter who wants job listings that are actually Job Opening records, a practice that wants a booking form writing straight into the system — those are projects where Webflow means building and maintaining an integration layer, and where WordPress means a plugin stack you will be patching for years. Builder removes the integration because there is nothing to integrate.

If it does not — if it is a brochure site — then Webflow is a better tool and the sensible answer is to say so. Running a Frappe instance to serve five static pages is not a saving.

The cost picture favours it either way. Webflow is dollar-priced per site and per seat, and that cost compounds across a client portfolio while the rand moves against you. Builder's licence is free and MIT, so an agency's exposure is hosting plus labour, both of which can be rand-denominated. And because published pages carry no vendor runtime, they survive the agency relationship ending — which is a thing SA clients have learned to ask about.
