tech/frappe · Raven · Skill Leaf

Team chat that can
read your ERP.

Raven is a Slack-style messaging platform built on the Frappe Framework — channels, threads, reactions, rich text, file sharing, and a React Native mobile app. Its reason to exist is the integration: a sales order in ERPNext can post itself into a channel with a preview, trigger a notification, and let someone action the workflow without leaving the conversation. Two things to know before you adopt it: it is not maintained by Frappe Technologies, and it is AGPLv3.

01 · What it is

Slack's shape, your database's contents.

Raven does what Slack and Microsoft Teams do at the messaging layer: channels organised by topic or project, direct messages, threaded replies, custom emoji reactions, rich text with code blocks and mentions, drag-and-drop file sharing, and GIF search. There is a web app and a mobile app. Dark mode ships. On the authentication side it supports the usual enterprise expectations — popular and custom OAuth providers, email-link login, two-factor over email, SMS or an authenticator app, and LDAP.

None of that is why you would choose it. You would choose it because it runs on the same site as your business data. Raven is a Frappe app, so a channel message can carry a live document preview of an ERPNext sales order, a Frappe HR leave application can raise a notification in a channel when it is submitted, and someone can perform a workflow action or print a document from inside the chat. The chat and the record are on one database, behind one permissions model.

The stack is React on the web with Radix UI and TipTap for the editor, React Native and Expo on mobile with NativeWind, and the Frappe Framework underneath doing Python, MariaDB or Postgres, Redis and socket.io. Push notifications and crash reporting run through Firebase.

Raven AI — agents that live in the channel

Raven ships an agent layer: you can build agents without writing code, and message them to automate tasks, extract data out of uploaded files and images, or run multi-step processes. Because the agent already sits inside a Frappe site, it reaches your doctypes through the same API and the same permission checks as a human user — which is a materially shorter path than wiring a Slack bot to an ERP over webhooks and a service account. If you are building an internal agent surface and you are already on Frappe, this is the cheapest place to put it.

02 · Who actually makes this

Not a Frappe Technologies app.

Raven appears in Frappe ecosystem listings and installs like any other bench app, which makes it easy to assume it carries the same backing as ERPNext or Frappe HR. It does not, and the difference is worth a minute of your attention before it goes into a client stack.

The point is narrower: if your client's risk register asks "who do we call and what have we bought", the honest answer for Raven is different from the answer for ERPNext, and you should give the honest answer up front rather than discover it during a security review. Budget for the possibility that you are the support tier.

03 · The licence

AGPL, and it reaches over the network.

Raven is licensed AGPLv3. The clause that distinguishes AGPL from GPL is the network one: if you modify the software and let users interact with it over a network, you are obliged to offer those users the modified source. Running an unmodified Raven for your own staff triggers nothing. Forking it, changing it, and putting the result in front of customers as part of a product is where the obligation lands.

Most South African implementation work is safely inside the boring case — install it, configure it, use it internally. The case worth flagging early is the one where a client wants Raven's chat surface embedded in a customer-facing portal with your modifications in it. That is a conversation to have with a commercial lawyer at proposal stage, not at go-live.

"Frappe is MIT" is only true of the framework

A common and expensive misreading. Frappe Framework itself is MIT. Almost nothing else in the suite is. ERPNext and Frappe HR are GPLv3. Helpdesk, CRM, Books, Drive, Learning and Print Designer are AGPLv3. Wiki and Builder are MIT. Raven is AGPLv3. If you are assembling a stack and someone on the account has written "MIT-licensed open source" into a proposal, check each app individually — the suite does not share one licence, and the differences are not cosmetic.

04 · How it works

Messages are doctypes.

Nothing special is happening under the chat. A channel is a document, a message is a document, and the whole thing is reachable over the standard Frappe REST API — which is what makes posting into a channel from a server script a two-line job.

# Post a message into a channel from a server script or external service
POST /api/resource/Raven Message
{
  "channel_id": "operations-jhb",
  "message_type": "Text",
  "text": "Stock take variance flagged on WH-CPT-01."
}
# Fire a channel message when a Sales Order is submitted.
# hooks.py in your own custom app — never edit Raven itself.
doc_events = {
    "Sales Order": {
        "on_submit": "my_app.notify.sales_order_to_raven",
    }
}

# my_app/notify.py
import frappe

def sales_order_to_raven(doc, method):
    frappe.get_doc({
        "doctype": "Raven Message",
        "channel_id": "sales",
        "message_type": "Text",
        "text": f"{doc.name} submitted - {doc.customer}, {doc.grand_total}",
    }).insert(ignore_permissions=True)
# Production install via the easy-install script
wget https://frappe.io/easy-install.py

python3 ./easy-install.py deploy \
    --project=raven_prod_setup \
    --email=you@example.co.za \
    --image=ghcr.io/the-commit-company/raven \
    --version=stable \
    --app=raven \
    --sitename chat.example.co.za
05 · Gotchas

Where it gets tricky.

Real-time chat means socket.io must actually work

Raven depends on Frappe's socket.io layer for live message delivery. Behind a reverse proxy that has not been configured to pass WebSocket upgrades, the app loads, messages send, and nothing appears until you refresh — which reads to users as "the chat is broken" rather than "the proxy is misconfigured". Test WebSocket upgrade before you test anything else.

Push notifications route through Firebase

The mobile app uses Firebase for push, crash analytics and performance monitoring. That is a Google dependency sitting outside your Frappe site, and it means device tokens and notification metadata leave your infrastructure. For a client who chose self-hosted Frappe specifically to keep data in-house, this deserves a line in the POPIA assessment rather than a shrug.

The mobile app needs a development build, not Expo Go

Raven's mobile app is React Native on Expo but requires an Expo Development Build. If you are planning to hand a tester a QR code and have them open it in Expo Go, that will not work. Shipping your own build means EAS, Xcode and/or Android Studio, and app-store accounts — a real piece of project scope, not an afternoon.

Chat volume is write-heavy in a way ERP data is not

An ERPNext site handles hundreds of documents a day. A busy chat channel handles that before lunch, plus the file uploads. Sizing the site for the ERP workload and then adding Raven to it is the standard way to discover your database and storage plan were tuned for the wrong shape of traffic. Watch disk on file attachments in particular.

Never patch Raven in place

The usual Frappe discipline applies with extra force here, because you are tracking an upstream you do not control. Put your event handlers and customisations in your own app and wire them through hooks.py. Editing the Raven app directory is how a routine bench update becomes a lost afternoon — and, under AGPL, how you quietly become the party with a source-offer obligation.

06 · Decision guide

Use it for, skip it for.

Use Raven when

  • You are already running Frappe and want chat where document context arrives automatically rather than as a pasted link.
  • Per-seat Slack or Teams licensing is a real line item and the team is large enough for it to matter in rands.
  • You want an internal agent surface and would rather build it against doctypes and permissions you already have than against a Slack app manifest.
  • Data residency is the reason you self-host Frappe, and moving internal conversation off a foreign SaaS is part of the same argument.
  • Your notification needs are document-driven — submissions, approvals, exceptions — rather than general-purpose messaging.

Skip Raven when

  • The organisation already lives in Teams or Slack. Chat tools win on network effect, not features, and a second one splits the conversation rather than replacing it.
  • You need external federation — shared channels with clients or suppliers on their own tenancy. This is an internal tool.
  • Voice and video calling are load-bearing. Raven is messaging; your meetings stay wherever they are now.
  • You need a vendor to call at 02:00. There is no first-party support contract, and the maintainer is an independent company, not Frappe.
  • Your legal position cannot absorb AGPL, or you intend to modify it and expose it to customers over a network.
  • You are not otherwise on Frappe. Standing up a Frappe site to get a chat app is the tail wagging the dog — the integration is the whole value, and without the rest of the stack there is nothing to integrate with.
07 · South African context

Where this lands in SA delivery.

The per-seat maths is the opening argument, not the closing one

Collaboration SaaS is dollar-priced and billed per user per month, so a 120-person organisation carries a four-figure USD annual line that moves with the rand and not with anything the business did. Self-hosted Raven converts that to infrastructure you already run. The honest counterweight: you are trading a licence fee for operational load — socket.io, storage growth, backups, upgrades, and being your own first line of support. For an organisation that already operates a Frappe site properly, that load is close to marginal. For one that does not, it is a new job.

POPIA · internal chat is personal information too

Conversations about customers are processing of personal information, and chat logs are frequently the least-governed data an organisation holds. Bringing them onto a site you control makes the residency and access questions answerable, which is a genuine improvement over a foreign SaaS tenancy. Two caveats stop it being a clean win: the Firebase dependency for mobile push moves notification metadata offshore, and you now own retention. Decide the retention period deliberately and configure it — an unbounded chat archive is a subject-access request you cannot answer efficiently and a breach that is worse than it needed to be.

Mobile-first is the right instinct here

For distributed teams — sites, warehouses, field service — the mobile app is the product, not a companion to it. Weigh that against data cost and intermittent connectivity: a chat client that syncs an image-heavy backlog over mobile data is a support call about someone's airtime. Set expectations about attachment sizes with the client before rollout rather than after the first invoice.
