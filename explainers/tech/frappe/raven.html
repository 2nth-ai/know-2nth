tech/frappe · Raven · Skill Leaf

Chat that shares
a database with your ERP.

Raven is an open-source messaging platform on the Frappe Framework. Channels, DMs, threads, reactions, a React web app and a React Native mobile app. The reason to run it is not the chat — it is that a purchase order can be approved inside the conversation, because the message and the document live in the same database under the same permissions.

01 · What it is

Team chat that can read your ERP.

A Slack-shaped chat app whose real differentiator is that it lives inside the same database as your business data.

Raven is an open-source messaging platform built on the Frappe Framework. Channels, direct messages, threads, reactions, rich text, file and GIF sharing — the shape is familiar if you have used Slack or Mattermost. The reason it exists is the second half: it sits on the same site as ERPNext, Frappe HR, or Frappe CRM, so a message can carry a live document and a document event can post a message.

That is the whole argument. Slack is a better chat app in isolation, and nobody serious disputes that. But Slack talks to your ERP through a connector you build and maintain, authenticated as a bot, with its own permission model bolted on the side. Raven talks to your ERP because it is your ERP — same doctypes, same users, same role permissions, same audit trail. If you already run Frappe, the integration work you would otherwise do is simply absent.

Licensed AGPL v3. Latest tagged release at the time of writing is v3.0.0, which introduced workspaces — a tenancy layer above channels, so one site can host several separated groups of channels and members.

02 · How it is built

React on the front, Frappe underneath.

The backend is ordinary Frappe: Python, MariaDB or Postgres, Redis, and socket.io for the realtime transport. Messages, channels and reactions are doctypes, which is why the REST API works on them without anyone writing a messaging API.

The frontend is where Raven breaks from the rest of the ecosystem. Most Frappe apps — CRM, Helpdesk, Builder, Learning — are Vue 3 on frappe-ui. Raven is React, using the Frappe React SDK for auth and data fetching, with Tailwind, Radix UI for accessible primitives, and TipTap for the rich-text composer. The mobile app is React Native on Expo with NativeWind.

Worth knowing before you commit, because it is a real cost and not a detail: if your team has built Vue skills across the Frappe stack, Raven is the one app where that does not transfer. Customising the Raven frontend means a second toolchain. Push notifications, crash reporting and performance monitoring go through Firebase, which is a Google dependency you are inheriting whether or not the rest of your stack is Google-free.

Where the ERP integration actually bites

Raven can render a previewable card for an ERPNext document inside a message, trigger a notification from a document event, run a workflow action from the chat surface, and print a document without leaving the conversation. In practice this is the feature that earns it a place: approvals stop being a context switch. The approver sees the purchase order in the channel, acts on it there, and the audit trail lands in the ERP rather than in a chat export nobody can query.

41 doctypes, and that is the point

Raven ships around forty doctypes. Every one of them is queryable over the standard Frappe REST API with the standard permission model applied. There is no separate messaging API to learn and no bot token to provision — an agent that can already read your ERP can read and post chat with the same credentials and the same role restrictions.

04 · Raven AI

No-code agents, with the usual caveats.

Raven AI lets you define an agent as a document rather than as code. A Raven Bot gets an instruction prompt, a set of Raven AI Function entries describing what it is allowed to do, and optional file sources to ground on. Users then talk to it in a channel or DM and it can extract data from attached files and images, call the functions you gave it, and chain several steps.

The honest read: this is genuinely useful for bounded internal tasks — "pull the open invoices for this customer", "file this scanned delivery note", "summarise what changed on this project this week". It is a configuration surface over tool-calling, and the no-code framing is accurate for that scope.

It is not an agent platform. There is no evaluation harness, no versioned prompt history, no tracing you would want for a workload that matters, and the function surface is whatever you whitelisted. Treat it as a convenient front door to your own data for staff, not as the place you build a customer-facing agent. If the task needs real orchestration, run it in a proper framework and let Raven be the interface.

POPIA note on the AI path

Raven AI calls out to whichever model provider you configure, which means message content and attached document contents leave your infrastructure. If the channel carries personal information — and in an ERP-adjacent chat tool it very often does — that is a cross-border processing decision under POPIA, not a feature toggle. Decide which workspaces may have AI enabled before you turn it on, document the basis for the transfer, and keep the agent off the channels where payroll, medical or client PII circulates.

05 · How it works

REST against the conversation.

Messages are documents, so the API you already use for invoices posts chat.

# Post a message to a channel
POST /api/resource/Raven Message
{
  "channel_id": "procurement",
  "text": "PO-2026-00412 is awaiting your approval.",
  "message_type": "Text"
}

# List recent messages in a channel
GET /api/resource/Raven Message
  ?filters=[["channel_id","=","procurement"]]
  &fields=["name","owner","text","creation"]
  &order_by=creation desc
  &limit_page_length=50
# Wire an ERP document event to a channel with no code at all:
# create a Raven Document Notification instead of a server script
POST /api/resource/Raven Document Notification
{
  "document_type": "Purchase Order",
  "send_alert_on": "Submit",
  "channel": "procurement",
  "message": "{{ doc.name }} submitted by {{ doc.owner }} — {{ doc.grand_total }}"
}
06 · Gotchas

Where it gets tricky.

Realtime depends on socket.io being right

Chat is the one workload where the realtime layer is not optional. If socket.io is misconfigured behind your reverse proxy — wrong upgrade headers, a load balancer that will not hold websockets, or Redis not shared across workers — Raven degrades to something that only updates on refresh. Test websockets through the full production path, not against bench start.

Firebase is a hard dependency for push

Mobile push, crash analytics and performance monitoring route through Firebase. If your organisation has ruled out Google processors, you lose mobile notifications, and there is no drop-in substitute. Settle this with whoever owns your data-processing register before you promise the mobile app.

React frontend is the odd one out

Every other Frappe app you are likely to run is Vue on frappe-ui. Raven is React. Shared component work, in-house UI conventions and developer familiarity do not carry across, so budget for a second frontend skillset if you intend to customise.

It is not a Slack migration target

There is no supported Slack import, no equivalent of Slack Connect for talking to other organisations, and the third-party app ecosystem is effectively nil. Moving an existing Slack workspace here means losing history and rebuilding every integration by hand.

Workspaces are new

The workspace tenancy model arrived with v3.0.0. If you are designing a multi-entity deployment around it, treat it as young: test member visibility and channel isolation against your actual org chart rather than assuming it behaves like a Slack Enterprise Grid.

Chat retention is now your problem

Self-hosting means no vendor is quietly expiring old messages for you. Conversations accumulate, attachments accumulate faster, and under POPIA you are expected to not keep personal information longer than you need it. Set a retention rule and a storage alarm on day one.

07 · Decision guide

Use it for, skip it for.

Use Raven when

  • You already run Frappe or ERPNext and want approvals and document chatter in the same system as the documents.
  • Per-seat chat licensing has become a real line item and your headcount is growing.
  • You need chat data to stay on infrastructure you control — a POPIA, sector-regulator or client-contract requirement rather than a preference.
  • You want document events to post to channels without building and maintaining a connector.
  • Your users are mostly internal staff already logging into the Frappe site every day.

Skip Raven when

  • Chat quality is the product requirement. Slack and Teams are better chat applications and it is not close.
  • You need to talk to clients and suppliers in shared channels — there is no federation story.
  • You depend on a connector ecosystem. The integrations you take for granted elsewhere do not exist here.
  • You are migrating an existing workspace and need the history to come with it.
  • You are not already on Frappe. Standing up and running a Frappe site purely to get chat is a bad trade — take Mattermost or Zulip instead.
  • Google processors are off the table and mobile push is non-negotiable.
08 · South African context

Where this lands in SA delivery.

The commercial case is clearer here than in a dollar economy. Per-seat chat is billed in US dollars; an organisation of 150 staff on a paid Slack tier is carrying a rand cost that moves with the exchange rate and ratchets up at every renewal. Raven's licence cost is zero and the running cost is a VM, so the FX exposure drops to whatever you pay for hosting — and if that hosting is local, to nothing.

The data-residency case is the stronger one. Internal chat in an ERP-connected tool ends up carrying ID numbers, salary queries, client details and medical certificates, because that is what staff do in chat regardless of policy. Under POPIA that makes your chat tool a processing system holding personal information, and Section 72 governs sending it across the border. Self-hosting Raven on infrastructure in South Africa removes the cross-border question for the chat itself — though not for Raven AI, which calls out to a model provider, and not for mobile push, which goes through Firebase.

Where it tends to work in practice: SA manufacturers, distributors and professional-services firms already running ERPNext, where the chat tool is for staff rather than clients and the approval workflow is the actual pain. Where it tends to fail: organisations whose real collaboration happens with people outside the company, which in SA professional services is a great many of them.
