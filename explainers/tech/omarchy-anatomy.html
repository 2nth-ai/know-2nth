tech · Platform & desktop

One keypress, one agent, write access to your desktop.

The workstation leaf makes the argument for an agent-editable operating system. This one opens the machine up. It is a map of a real Omarchy 4.0.4 install — which files the system is made of, which of them are yours, how a keybinding becomes a coding agent with permission to change them, and the one safety net Omarchy leaves for you to build.

01 · What this is

Two layers of text files and a pile of shell scripts.

Underneath the theme switcher and the launcher, Omarchy has a simple shape. Omarchy owns one read-only tree, you own another, and about four hundred commands connect them. Once you can see that split, every question about where a change should go answers itself, and so does the question of what an agent is allowed to touch.

Omarchy owns

/usr/share/omarchy

Installed by pacman as the omarchy package. Default Hyprland Lua, the shell, 22 themes, 106 migrations, the agent skills, and every omarchy-* command. Updates replace it wholesale.

You own

~/.config

hypr/*.lua overrides, omarchy/ hooks, themes, menu extensions, plugins and your default-agent choice. Nothing in an update writes here except a migration.

The glue

omarchy-* commands

441 bash and Python scripts on the path. The biggest families are install (38), theme (34), hardware (26), remove (25), launch (24) and hyprland (24). Every keybinding and menu item ends up calling one.

The face

omarchy-shell

One Quickshell (QML) process that draws the bar, launcher, menus, notifications and lock screen. It also hosts the agents panel that shows your model usage.

02 · How it is wired

Your config loads last, so it wins.

The load order is the whole design. ~/.config/hypr/hyprland.lua is short. It dofiles Omarchy's bootstrap, requires default.hypr.omarchy, and only then loads your hypr.monitors, hypr.input, hypr.bindings, hypr.looknfeel and hypr.autostart. The defaults can improve on every update without touching your files, and anything you set overrides them. You can switch off all of Omarchy's default bindings with a single flag, omarchy_default_bindings = false.

Hyprland 0.56 is configured in Lua now, not hyprlang. The bootstrap keeps a list of module prefixes (default.hypr, hypr, omarchy.current.theme) that it drops from Lua's module cache on reload. A saved edit is live straight away, with no logout and no restart. That matters a great deal once an agent is the one doing the editing.

Themes are templates. omarchy-theme-set renders .tpl files with the theme's colours, restyles the shell and apps, then runs omarchy-hook theme-set. That calls whatever you have placed in ~/.config/omarchy/hooks/theme-set.d/. The same hook mechanism covers post-boot, post-update, font-set, battery-low and pre-refresh-pacman.

Updates are pacman plus migrations. omarchy-update pulls the new package, then runs any of the 106 dated migration scripts that have not run yet. Migrations are the one place where Omarchy deliberately reaches into ~/.config.

03 · The agent loop

From keypress to edited config with no approval prompts.

This is the part that makes Omarchy 4 agent-driven rather than just agent-friendly. Every step is a short, readable script, and reading them is the best way to understand what you have agreed to.

Interactive: pan, zoom, trace. Open full screen ↗

  1. You pick an agent once. omarchy default agent claude writes one word to ~/.config/omarchy/defaults/agent. Omarchy deliberately ships without a default, and the keybinding opens a picker until you choose one.
  2. The launcher pre-approves it. omarchy agent starts the chosen agent with that agent's own way of saying "don't stop to ask": claude --permission-mode auto, gemini --yolo, copilot --allow-all, grok --permission-mode bypassPermissions, crush --yolo, opencode --auto. The comment in the script spells out the reasoning: agents launched from a keybinding run unattended.
  3. It moves out of your home folder. If ~/Work exists, the launcher switches into it first, because agents refuse to remember trust for $HOME. The working directory is the agent's first view of the machine.
  4. Skills tell it where things are. Omarchy ships two agent skills, omarchy (Hyprland, theming, hooks, plugins, captures) and diagnose-crash, and symlinks them into the agent's skills folder. The agent arrives already knowing that edits go in ~/.config/hypr and never in /usr/share/omarchy.
  5. It edits, Hyprland reloads. The agent changes a Lua file, Hyprland picks it up, and you see the result straight away. The loop closes without you approving anything.
  6. Crashes and spend get the same treatment. omarchy agent crash <pid> gathers the facts from coredumpctl and briefs the agent through the crash skill. The shell's agents panel reads omarchy-agent-usage-*, which collects local transcript stats together with the provider's rate-limit endpoint.

One correction to the launch coverage. The release was pitched as the OS offering your agent the core dump when a process crashes. On the 4.0.4 install we mapped, the command and the skill are both present, but nothing in the shell or the package calls them automatically. Treat crash triage as a command you run by PID, not a pop-up you can count on.

04 · Where changes belong

A routing table for you and your agent.

Most Omarchy breakage comes from an edit in the wrong layer. That is equally true when the agent made it.

You want to changeEditNever
Keybindings~/.config/hypr/bindings.luadefault/hypr/bindings/*
Monitors, input, gaps, animations~/.config/hypr/{monitors,input,looknfeel}.luaThe bootstrap or omarchy.lua

The tell that it is working: look at ~/.config/hypr after a few weeks of agent-assisted changes and you will find bindings.lua.bak.<epoch> files next to the real ones. The agent backs up before it writes, which is good manners. It is not version control.

05 · Decision guide

When to let the agent drive.

Auto mode is the default from the keybinding, and you can turn it off. Make that choice deliberately rather than inheriting it.

Let it drive when

  • ~/.config is a Git repo and you commit before each session
  • The change is cosmetic or reversible: bindings, gaps, themes, widgets
  • You are diagnosing, not changing, for example crash triage from a core dump
  • The machine is yours and nobody else depends on it being up

Take the wheel when

  • The change touches boot, disk encryption, drivers or pacman
  • The agent wants to edit /usr/share/omarchy. That is a bug report, not a fix
  • Client credentials or SSH keys live in the working directory
  • You cannot say which file changed. Launch it from a terminal without the auto flag instead
06 · South African context

The meter in the bar is in dollars.

Spend is visible, so use it. The agents panel sits next to the battery for a reason. Every "make my bar look nicer" session draws on a subscription billed in USD. Small cosmetic changes are cheaper to make by hand once you know which file to open, and section 04 is that list.

Rolling updates on capped data. omarchy-update is pacman plus migrations, and both are bandwidth. On LTE, update deliberately rather than whenever the indicator nags. If you run several machines, keep a local package mirror.

Your ~/.config repo is also your second machine. Plenty of local developers run two boxes, one for client Windows and M365 work and one for building. If the Omarchy layer is text in Git, rebuilding or cloning it after a theft or a dead SSD takes an afternoon rather than a week.
