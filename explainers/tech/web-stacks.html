tech · Modern web stacks · Skill Leaf

The web stack, rebuilt for agents.

The 2024–26 reshuffle of the modern web: the monolith split into a structured-content CMS layer (Sanity, Payload, Directus, Strapi), an islands-first framework layer (Astro, Next.js, SvelteKit), and edge-rendered hosting (Cloudflare, Vercel, Netlify). Three things changed in 2026 that the earlier version of this page could not have said. Cloudflare acquired Astro in January, collapsing the framework and hosting layers into one vendor. MCP stopped being a wrapper and became a shipped feature in every serious CMS. And the delivery layer grew a policy dimension — your robots.txt is now a commercial document. Meanwhile WordPress logged 11,334 new CVEs in 2025, 91% of them in plugins. This leaf maps the current baseline and the top 5 MCP-ready web surfaces.

01 · What's wrong with WordPress

The plugin attack surface caught up with the platform.

WordPress still powers a sizeable share of the public web. The 2026 problem is not the core, which is mature and well-maintained — it is the plugin ecosystem that the platform's success was built on. Patchstack's State of WordPress Security in 2026 report logged 11,334 new vulnerabilities in 2025, up 42% year-over-year. The split is the part that matters: 91% in plugins, 9% in themes, and six in core — all six rated low risk. More high-severity issues were found in 2025 than in the previous two years combined (1,966, or 17% of the total). The weighted median time from public disclosure to first exploitation in the wild is five hours, and close to half of the disclosed vulnerabilities had no patch available at the moment they went public.

The comforting assumption — "our host has a WAF" — does not survive the data either. In Patchstack's large-scale pentest of popular hosting companies, only 26% of vulnerability attacks were blocked. Managed hosting reduces the exposure; it does not remove it.

The architectural story matches the security story. Traditional WordPress generates HTML on every request from PHP against MySQL; modern web stacks pre-build pages as static HTML or render them at the edge, delivering sub-100ms response times globally. Astro's homepage cites Core Web Vitals pass rates of 66% for Astro sites vs. 48% for WordPress and 30% for Next.js — numbers that should be checked against current Chrome UX Report data, but that direction-of-travel is correct.

The third problem is multi-channel. A WordPress install ships one website. A modern stack assembles content once in a structured CMS and renders it across web, mobile, kiosk, voice, and now agent surfaces — including via Model Context Protocol so an AI agent can read or update the same content store.

The compliance clock is the new argument

The security case used to be a technical preference. In 2026 it acquired a regulatory edge: under the EU Cyber Resilience Act regime, commercial WordPress plugins need a vulnerability disclosure programme in place to be made available to European users. For an SA agency shipping sites for clients with EU customers, "we run 24 plugins from 19 vendors" becomes a question you have to answer with evidence rather than a shrug.

Headless WordPress is the bridge, not the destination

Many teams in 2026 sit in headless WordPress — running WP-as-CMS behind an Astro or Next.js front-end. This reduces the public attack surface (the admin is isolated from the rendered site) and recovers most of the performance gap. It does not solve the structured-content or agent-readiness problem — WordPress's post-and-page model and lack of native MCP support remain limits. Headless WP is a sensible migration step; not an endpoint.

02 · The modern web stack

Three layers, separately replaced.

The 2024–26 evolution split the WordPress monolith into three clear layers, each with multiple credible options. Each layer can be swapped without touching the others. This is the structural shift — not a single replacement product, but a re-architecture into composable parts.

Layer 1 · content

Structured CMS

Schema-as-code, JSON-document store, API-first. Editors get a custom Studio; developers query structured fields, not HTML. Sanity, Payload, Directus, Strapi.

Layer 2 · rendering

Islands framework

Server-renders HTML, ships minimal JS, hydrates only the interactive bits. Astro is the reference; Next.js / Remix / SvelteKit / Qwik are the alternatives.

Layer 3 · delivery

Edge hosting

Static assets to edge POPs; SSR at the edge for dynamic routes. Cloudflare Pages, Vercel, Netlify. Sub-100ms TTFB globally; auto-scaled per request.

MCP is the fourth (cross-cutting) layer — and it stopped being a wrapper

The Model Context Protocol is not a separate layer of the stack — it is the integration surface every credible CMS now ships. The status changed materially during 2026. Strapi's MCP server went GA in v5.49.0 — built in, with every operation gated by admin-token permissions rather than bolted on by a community package. Directus 11 ships native MCP plus an AI assistant wired to OpenAI, Anthropic and Gemini. Sanity exposes content via its own MCP server for Claude Code, Cursor and v0. Payload exposes one too. Astro ships an official MCP server and context files. A year ago "MCP-ready" meant somebody had written a wrapper; today it means the vendor ships and supports it. That is the difference between a demo and a dependency you can put in a proposal.

Two of the three layers just consolidated

The clean separation above is still architecturally true, but the vendor map behind it shifted in 2026. Cloudflare acquired The Astro Technology Company on 16 January 2026 — the framework layer and one of the three hosting options are now the same company. Figma acquired Payload (announced June 2025), putting a CMS inside a design tool. Composability survives; independence is thinner than the diagram suggests. Section 04 covers what that actually costs you.

03 · Sanity

The Content OS for the AI era.

Sanity positions itself as "the Content Operating System for the AI era" — not a traditional headless CMS, but a structured-content platform built for programmatic operations at scale. The underlying technical claims:

  • Content Lake — a JSON-document store with schemas defined in code rather than enforced at the database layer. Allows flexible content modelling without database migrations.
  • GROQ — Sanity's proprietary query language for filtering and joining structured content. SQL-shaped semantics; JSON-document target.
  • Sanity Studio — a customisable, multiplayer-capable editorial interface built on React. Same Studio binary; per-customer custom workflows.
  • API-first architecture — every operation goes through HTTP APIs, supporting real-time listening and webhook-driven automation.

Sanity has raised north of $51.8m and counts Linear and Anthropic among its published users — useful when the objection in the room is "nobody serious runs a headless CMS."

The 2026 AI / agent positioning is the bigger story. Sanity ships Content Agent (transforms source materials into structured content; audits and edits at scale; supports visual editing via natural language), Agent Actions (schema-aware AI automations triggered by content mutations), and Agent Context (surfaces structured data for agentic reasoning). The Sanity MCP server integrates with Claude Code, Cursor, and v0 — an agent can read or write Sanity content through standard MCP without bespoke integration code.

What makes Sanity structurally different from WordPress

WordPress's data model is "posts and pages with custom fields bolted on." Sanity's data model is "schemas you define in TypeScript, with arbitrary nested structures, references, and validation, queryable by GROQ." When an agent (or a human) wants the "list of all case studies tagged AgentForce, with their associated services, ordered by published date," Sanity answers that in one query. WordPress answers it after three plugins, two custom hooks, and a partial cache rebuild.

04 · Astro

Islands architecture, zero JS by default — now owned by Cloudflare.

Astro is a JavaScript web framework optimised for fast, content-driven sites. Components render on the server and ship lightweight HTML to the browser with zero unnecessary JavaScript overhead. The defining feature is Islands Architecture — pages are static HTML by default, with hydration applied only to the interactive components ("islands") that need it. The rest of the page never ships its rendering JS to the client.

The ownership changed on 16 January 2026. Cloudflare acquired The Astro Technology Company — Fred Schott and the core team — with a public commitment that "Astro will remain open source" under Cloudflare's stewardship, and continued backing for the Astro Ecosystem Fund alongside Webflow, Netlify, Wix and Sentry. Astro 6 went into beta the same week and shipped stable in March; Astro 7 landed on 22 June 2026 and is the current line (7.2 as of early August).

Key technical traits:

  • Framework-agnostic UI — React, Vue, Preact, Svelte, and Solid all work in the same project. "Zero lock-in" is the positioning.
  • Content Collections — type-safe Markdown / MDX organisation with frontmatter validation. Schema in code; types flow through to the templates.
  • File-based routing, server-side endpoints, view transitions, image optimisation built in.
  • Actions — type-safe backend functions callable from frontend code, no separate API surface required.
  • Hosting adapters for Vercel, Netlify, Cloudflare, AWS, and Deno — same code, different deploy target. Route caching went stable in 7.0, with CDN cache providers for all three major hosts.
  • Rust all the way down (7.0) — the .astro compiler rewritten in Rust, Markdown/MDX through a new Rust pipeline, queue-based rendering, and Vite 8 with the Rolldown bundler. Builds measured 15–61% faster than Astro 6.
  • Advanced routing (7.0) — a src/fetch.ts entrypoint giving full control of the request pipeline, Hono-compatible.

The agent story went past MCP in 7.0, and this is the part worth noticing. Astro ships an official MCP server and context files, so Claude Code / Cursor / Windsurf can introspect routes, content collections and components. But 7.0 added something more pointed: the dev server detects that a coding agent is driving it, runs itself in the background rather than holding a terminal, emits structured JSON logs instead of human-formatted output, and exposes a health endpoint at /_astro/status. The framework now has a different mode for machine operators. That is the same move Omarchy made at the OS layer — agent as a first-class user of the tool, not a visitor.

Core Web Vitals as the headline pitch

The figure held through 2026: 66% of real-world Astro sites record good Core Web Vitals, against 48% for WordPress, 47% for Gatsby, 30% for Next.js and 28% for Nuxt. Direction-of-travel matches the architecture: less shipped JS → lower TBT and INP → more sites pass. These are Chrome UX Report-derived and they shift quarterly, so re-check before putting a number in a proposal — but the ranking has been stable, and it is the ranking, not the decimal, that wins the argument.

The honest cost of the acquisition

Cloudflare owning Astro is mostly good news: a framework that was funded by consultancy and sponsorship now has a balance sheet behind it, and the Astro-on-Cloudflare path becomes first-party rather than adapter-shaped. Astro 7's route caching and CDN providers still ship for Netlify and Vercel, and the licence is unchanged.

Plan for the direction anyway. A framework maintained by a hosting company optimises, over time, for that company's platform — not through malice but through where the maintainers' problems come from. If you pick Astro and Cloudflare you get a genuinely tight stack and you have concentrated two layers with one vendor. If you pick Astro on Vercel or Netlify, keep the adapter path in your regression tests rather than assuming it stays equally exercised. This is a watch-item, not a reason to switch.

05 · The top 5 MCP-ready web surfaces

What the modern stack ships through.

Five distinct shapes of web surface, each MCP-ready in 2026. The list mixes CMS and framework deliberately — the right combination depends on whether content workflow or front-end DX is the bottleneck.

1. Sanity

CMS · content OS
Structured content, GROQ queries, Content Lake · sanity.io

The structured-content platform with the strongest agent positioning. Content Agent for natural-language editing, Agent Actions for schema-aware automation, Agent Context for agent-reasoning surfaces. MCP server integrates with Claude Code, Cursor, v0. Pairs naturally with Astro or Next.js on the front end.

Pick when: the editorial workflow matters more than the framework. Marketing / content-heavy / multi-locale.

MCP native GROQ Content Agent Studio (React)

2. Astro

Framework · islands
Server-first, islands hydration, Cloudflare-owned · astro.build

The reference islands-architecture framework, acquired by Cloudflare in January 2026 and still MIT-licensed. Astro 7 (June 2026) rewrote the compiler in Rust and moved to Vite 8 / Rolldown for 15–61% faster builds. Zero-JS default, content collections with TypeScript validation, official MCP server, and a dev server that detects coding agents and switches to JSON logs. The 2nth default front-end framework for content-driven sites.

Pick when: the site is content-led, performance is a buyer criterion, and the team can author in Markdown / MDX or query a headless CMS.

MCP native Astro 7 Zero JS default Cloudflare-owned

3. Payload CMS

CMS · code-first
TypeScript-native, Postgres / MongoDB, Figma-owned · payloadcms.com

Code-first headless CMS that runs in the same Next.js app as the front-end. TypeScript config, Postgres / MongoDB backends, full admin UI built in, and its own MCP server for agent read/write. Acquired by Figma in June 2025; the MIT licence and the repo stayed put, and Payload 4.0 is the first release built on Figma's design system — the strategic direction is design-to-production, components in Figma bound to real Payload data. The top choice for Next.js teams that want the CMS and the app deployed as one unit.

Pick when: the team is Next.js-native and wants a single deployable. Avoids the headless-API-as-network-call latency.

MCP server TypeScript Postgres / Mongo Figma-owned

4. Directus

CMS · SQL-first
Any SQL database, native MCP server, AI assistant · directus.io

Connects to any existing SQL database (Postgres, MySQL, MS SQL, SQLite) and exposes it as a content API + admin app. Directus 11 ships native MCP, an AI assistant wired to OpenAI / Anthropic / Gemini, and collaborative editing with live presence. The "uncompromising data ownership" pitch — the database stays where it lives; Directus wraps it.

Pick when: the data already lives in a SQL warehouse / OLTP store and the requirement is to expose it as a CMS without migrating.

MCP native SQL-first AI Assistant Self-hostable

5. Strapi

CMS · OSS default
Open-source Node.js headless CMS, largest plugin ecosystem · strapi.io

The open-source headless CMS with the broadest plugin ecosystem and the most mature self-hosting story. Node.js runtime; Postgres / MySQL / MongoDB backends; REST and GraphQL out of the box. The MCP server went GA in v5.49.0 — agents can create, read, update, publish and unpublish through the Content Manager, with every operation gated by admin-token permissions. The March–June 2026 releases also brought a customisable Blocks editor and live media preview.

Pick when: open-source self-hosting is the hard requirement, and the team can absorb operating the CMS infra themselves.

MCP built-in (GA) Open source REST + GraphQL Plugin ecosystem

Honourable mentions, not yet on the top 5

Storyblok for visual editing of marketing pages; Contentful as the legacy enterprise option (mature but expensive, MCP support via partners); Builder.io for AI-native visual building (Builder Composable + Visual Copilot); Webstudio as the open-source visual builder; NomaCMS as the AI-first newcomer with native Claude Code / Cursor MCP.

EmDash deserves its own paragraph now. Cloudflare launched it on 2 April 2026 and called it the spiritual successor to WordPress — fully open-source, serverless, written in TypeScript, with a plugin model where extensions run in isolated sandboxes and can only do what they explicitly request. That is a direct, well-aimed answer to the Patchstack numbers in section 01. It is also a v0.1.0 preview with a marketplace carrying fewer than a hundred plugins. Right architecture, empty ecosystem. Track it; do not stake a client engagement on it this year.

06 · Who is allowed to read your site

The delivery layer grew a policy dimension.

For twenty years robots.txt was a politeness convention with one question in it: crawl this, or don't. In 2026 it became a commercial document, because "crawl" stopped meaning one thing. Indexing a page so a human can find it, reading a page to ground an answer that human never leaves the chatbot to verify, and ingesting a page to train a model are three different transactions — and until recently your site could not tell them apart.

Signal 1

search

Index it and send people to it. The bargain the web has always run on — you get traffic in exchange for being crawled. Almost every publisher says yes.

Signal 2

ai-input

Read it to answer a question right now, in someone else's interface. You supply the substance; the referral may never arrive. This is where opinion splits.

Signal 3

ai-train

Ingest it into a training set. No traffic, no attribution, no recurring relationship. The signal most publishers set to no the moment they can express it separately.

Those three are Content Signals — a machine-readable vocabulary Cloudflare added to robots.txt, each a plain yes or no. It is not a technical control; it is a stated preference, in a format a crawler operator can no longer claim was ambiguous. That matters mostly for what it does to the argument afterwards.

The enforcement sits alongside it. Cloudflare blocks AI crawlers by default on sites that opt in, and it set a deadline: from 15 September 2026, AI companies that have not separated their search crawlers from their AI-training and agent crawlers get their mixed-use bots blocked by default on any page carrying ads. That is a structural push — it forces crawler operators to declare which of the three transactions they are actually doing.

Pay per crawl is the third piece and the most speculative: a price mechanism built on HTTP 402 Payment Required, with Cloudflare as merchant of record. Crawlers either declare a maximum price up front or respond to a 402 with one; publishers get paid per request. Early partners are Ceramic.ai and You.com, so this is a narrow market rather than a new revenue line. But it is the first time the exchange has had a number attached to it instead of an argument.

The llms.txt reality check

Anti-hype, because this one is being sold hard. Analyses spanning hundreds of millions of bot events show GPTBot and its peers fetching ordinary HTML and largely ignoring /llms.txt. The file's actual consumers today are agentic browsers, coding tools and Lighthouse — not the training crawlers it is usually pitched against.

Ship it anyway. It costs one generated file, it genuinely helps the agent surfaces that do read it, and this site publishes one alongside an MCP endpoint for exactly that reason. Just do not let anyone sell it to a client as an SEO product, and do not treat it as a substitute for the signals above — a preferences file nobody enforces is a wish, not a control.

What to actually do, in order

  • Decide the three answers before you write the file. Search yes is easy. The ai-input question is a business decision about whether being cited without a click is worth it — for a consultancy publishing to be found by buyers, usually yes; for a publisher selling ads against pageviews, usually not.
  • Put the signals in robots.txt and the enforcement at the edge. The declaration is evidence; the WAF rule is the control. Neither substitutes for the other.
  • Ship llms.txt and an MCP endpoint if you want to be readable by agents on purpose — that is the opt-in half of the same conversation.
  • Re-check after 15 September 2026. The mixed-use deadline will move some crawler traffic into new user-agents; whatever you measured before it will not describe what happens after.
07 · Decision guide

Which combination for which job.

Pick the CMS for the editorial workflow and the framework for the delivery constraint — in that order. The most common failure is choosing the front-end framework first because the developers had an opinion, then discovering the content model does not survive contact with the people who have to update it every week.

App with content + interactive features Payload Next.js Single deployable. Payload runs in the Next.js app; no separate CMS service to operate. Now Figma-owned, so the design-to-production path is where the roadmap is pointed.
Internal tool over existing SQL data Directus Astro or SvelteKit Database stays put; Directus wraps it; front-end framework is a style choice.

08 · South African context

FX, POPIA, and the agency-landscape question.

The WordPress install base is large — and creaking. Most SA SMB and mid-market websites are on WordPress. Many were built by agencies that no longer exist or no longer maintain them. The plugin-vulnerability surface is the most common single source of incidents the SA cybersecurity community sees. Replacing or hardening these sites is real work — budget the migration as a 4–12 week engagement, not a weekend.

POPIA fits modern stacks better than it fits WordPress. A headless CMS at africa-south1 or eu-west + a static front-end deployed to Cloudflare's African edge means personal data (form submissions, user accounts) lives in one residency-controlled store and the public site never holds it. WordPress's "everything is in one MySQL on one host" model makes Section 19 evidence harder to assemble.

Edge hosting and FX. Cloudflare Pages, Vercel, and Netlify are USD-priced; Cloudflare's free tier covers most small sites end-to-end. Bandwidth-sensitive workloads benefit from Cloudflare's African POPs (Cape Town, Johannesburg, Lagos, Nairobi, Cairo, Casablanca and others — see tech/cloudflare/edge-africa-me) over US-only Vercel routing for SA-resident readers.

Crawler policy is now part of the brief, and it is cheap here. SA publishers and content-led businesses already sit behind Cloudflare more often than not. Setting the three content signals costs nothing and takes minutes, and it is the only version of the "AI is eating our traffic" conversation that produces an artefact instead of a complaint. For a media client, get the ai-train answer on record from the business before a developer picks a default. For a consultancy or a services firm, the calculus usually runs the other way — being read and cited by an assistant is distribution, not theft.

Astro on Cloudflare is now a first-party path. That strengthens an argument this tree already makes: for SA-resident readers, serving from Cloudflare's African POPs beats US-routed hosting, and the framework layer is no longer a third-party adapter on top of it. The flip side is section 04's watch-item — if you standardise on Astro and Cloudflare, be honest in the risk register that you have consolidated two layers with one vendor.

Agency landscape shift. SA agencies that used to ship WordPress sites are migrating to "WordPress for editorial + Astro for the front-end" as the path of least client disruption. The Sanity / Payload / Directus conversation is happening with the technical-buyer cohort first; mainstream marketing teams catch up over the following 12–18 months.
