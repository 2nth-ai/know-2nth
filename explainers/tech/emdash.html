tech · EmDash CMS · Skill Leaf

WordPress's job, rebuilt for this decade.

EmDash is an open-source CMS from Cloudflare, built on Astro. It gives a client what they liked about WordPress, an admin screen where they write, preview and publish, and replaces what sat underneath: plugins run in a sandbox, content is structured data, and the site runs on Workers with a D1 database instead of a PHP server. Every site also ships with an MCP server, so an agent can edit it. This is what it is, how a build works, what our first deploy was really like, and when to leave it alone.

MIT licence Astro · TypeScript Workers · D1 · R2 MCP on every site v1.6 · young ecosystem
01 · What it is

A CMS with an admin screen, not a framework with a README.

EmDash describes itself as "the spiritual successor to WordPress: an open source, agent-ready, full-stack CMS for Astro". In practice it is an Astro integration (emdash) that adds an admin UI at /_emdash/admin, a database-backed content model, media storage, authentication with passkeys, and a set of APIs to a normal Astro project.

The split of responsibilities is the WordPress one. A developer builds the theme: Astro pages and components. An editor runs the site: pages, menus, media, drafts, scheduled posts. The difference is where things live. Content types are defined in the database and edited in a schema builder, TypeScript types are generated from that schema, and rich text is stored as Portable Text (structured JSON) instead of HTML mixed with shortcodes.

It is released under the MIT licence. The core packages follow semantic versioning and the project's README calls them stable and ready for production; first-party plugins and the plugin tooling are still on 0.x. Version 1.6 shipped on 23 November 2026, the third release in four weeks.

The mental model

Think of it as WordPress's contract with the client, on Astro's contract with the developer. The client gets a login and can change their own site. The developer gets typed content, components and a Git repo, with no PHP, no server to patch and no plugin that can read the whole database.

03 · In practice

From nothing to an admin screen.

The scaffolder asks for a platform (Node or Cloudflare) and a template (blog, starter, marketing, portfolio). On Cloudflare the first deploy creates the D1 database and R2 bucket named in the Wrangler config.

# Scaffold the marketing template for Cloudflare
npm create emdash@latest my-site -- --template cloudflare:marketing --yes

# Local: site on :4321, admin at /_emdash/admin (setup wizard on first visit)
npm run dev

# Check the first-run schema and content before it is applied
npx emdash seed seed/seed.json --validate

# Build and deploy; D1 and R2 are provisioned on the first run
npm run deploy
---
// src/pages/[slug].astro: one route renders every page an editor creates
import { decodeSlug, getEmDashEntry } from "emdash";

const slug = decodeSlug(Astro.params.slug);
const { entry: page } = await getEmDashEntry("pages", slug);
if (!page) return Astro.rewrite("/404");
---

The seed file is the handover document

seed/seed.json declares the block types, collections, menus, settings and first content in one file, and the setup wizard applies it once. That makes a client site reproducible: the same repo and seed give you the same starting site on a laptop, on staging and in production. After setup the database is the source of truth, so treat the seed as a starting point, not a deploy step.

04 · The honest bit

What our first Workers deploy was actually like.

We rebuilt a seven-page agency site on EmDash 1.6 on 24 November 2026: the marketing template, one custom block, one API route, deployed to Workers with D1 and R2. One working session, with an agent doing the typing.

What went well. The scaffold produced a working site with eleven block types, and it ships agent instructions and a docs MCP server in the repo, so a coding agent has the current API to hand. Re-skinning was a token file. Adding a block meant one entry in the seed and one Astro component, and the generated types followed. An ordinary Astro API route sat beside the CMS without ceremony.

What bit us. On a new database the Worker applies core migrations on the first request. There were 97. We set a secret seconds after deploying, which redeploys the Worker, and that killed the migration partway and left its lock held. Every request then answered 503 until the lock was released. The documented fix is emdash migrate, which needs a Cloudflare API token with D1 edit rights; a Wrangler login is not enough.

What to plan for. Passkeys are bound to the hostname used at setup, so set EMDASH_SITE_URL and the custom domain before you run the wizard. The wizard is open to whoever reaches it first, so finish setup straight after the first deploy. Back up EMDASH_ENCRYPTION_KEY; D1 cannot recover it. Sandboxed plugins need the Workers Paid plan; everything else here ran without it. The built-in search needs SQLite or D1, so a Postgres deployment gives that up.

Deploy order that avoids the trap

Create the secrets and the custom domain first, deploy once, then leave the Worker alone until the first request has finished migrating. For anything that matters, run migrations from CI with emdash migrate before the deploy, which is the path the docs recommend for production.

Practical guidance

If nobody but a developer will ever edit the site, a static site in Git is simpler and has less to go wrong: this tree is one. If a client needs to change their own pages, EmDash is now a credible answer where the choice used to be WordPress or a paid headless CMS. If the business depends on WooCommerce or a specific WordPress plugin, the ecosystem gap decides it for you.

06 · Decision guide

Reach for it when. Skip it when.

EmDash earns its place when a non-developer has to run the site. Without that requirement it is extra moving parts.

Reach for it when

  • A client or marketing team must edit pages without a developer
  • You are replacing a brochure or blog site on WordPress
  • You already build with Astro and deploy to Cloudflare
  • You want an agent to draft and update content through MCP
  • Permissive licensing and a clean exit matter to the client
  • You want drafts, previews, revisions and scheduling without buying a headless CMS

Skip it when

  • The site is a shop on WooCommerce, or leans on specialist WordPress plugins
  • Only developers edit it: static files in Git are simpler
  • You need a large pool of freelancers who already know the platform
  • The client needs a plugin that does not exist yet and has no budget to build it
  • You need a long support track record before you can commit
  • You want a database-free static build: the docs assume server rendering

Do the plugin inventory first

Before quoting a WordPress migration, list every plugin on the old site and what it does for the business. Content moves with the importer. Behaviour does not: forms, bookings, memberships and payment flows each need an EmDash plugin, an Astro route or an external service. That list is the real size of the job.

07 · South African context

A client-editable site without a server to babysit.

For SA agencies and small in-house teams the appeal is practical: fewer things to patch, pay for in dollars, or be phoned about on a Sunday.

Cost · little to rent

The software is free and there is no per-seat CMS fee priced in dollars. A small brochure site fits comfortably in Cloudflare's included usage; the main paid item is the Workers Paid plan if you want sandboxed plugins. Check current Cloudflare pricing before you quote, because image transformations and heavy traffic are billed separately.

Latency · served from Johannesburg and Cape Town

Workers run in Cloudflare's South African locations, so pages are rendered close to local visitors instead of on a shared host overseas. D1 is a single-primary database with read replication, so admin writes may travel further than page reads; for a content site that is rarely noticeable.

Skills · a small local pool, for now

There are many WordPress developers in South Africa and very few people who have shipped EmDash. A client who leaves you can take the site, because it is MIT-licensed Astro, but they will be hiring an Astro developer, not a WordPress one. Say that plainly in the proposal.
