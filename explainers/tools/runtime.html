Why we run on the Claude Agent SDK.

The 2nth.ai agent platform commits to one runtime: Anthropic's official Claude Agent SDK (claude-agent-sdk Python, @anthropic-ai/claude-agent-sdk TypeScript) — the same engine Claude Code itself runs on. This leaf documents the decision: the alternatives we weighed, what the SDK actually does for us, the implications you will run into in a real pilot.

01 · TL;DR

What the SDK is, in one paragraph.

The Claude Agent SDK is not a framework in the LangChain sense. It is a tight wrapper around the Anthropic API that adds the agent loop, MCP support, and a handful of primitives the platform needs: allowed_tools, disallowed_tools, PreToolUse hooks, structured output, and prompt caching. It is the same engine Claude Code itself runs on, which means partners reading the SDK docs already understand 80% of what we built. The full decision rationale — including the comparison table, the implications you should plan for, and the hook-composition gotcha — is in the sections below.

02 · Why this, not the alternatives 🔒

Five frameworks we passed on, with the reasons.

The agent-framework market in 2026 is crowded. Each has a real audience. Here is why none of them won the runtime layer for the 2nth.ai showcase — and the one consideration that decided it.

AlternativeWhy we passed
LangGraphBest-in-class for stateful multi-agent orchestration, but generic — partners would have to learn LangGraph and our wiring. Twice the surface to onboard onto.
CrewAIRole-based, fast adoption (60%+ Fortune 500 by Jan 2026), but coarser permission model. We would be papering over allowed_tools ourselves at exactly the load-bearing seam where we cannot afford bugs.
Vercel AI SDKTypeScript-only, lovely DX, but less aligned with how Anthropic ships MCP and Skills. We would pay a permanent catch-up tax as Anthropic's primitives evolve.
OpenAI Agents SDKLocks the runtime to OpenAI models. The whole point is to use Claude.
Build on the raw Anthropic APIWe would recreate the agent loop, context compaction, tool-result feeding, and MCP plumbing for no upside. The SDK gives us all four free.

The deciding factor. allowed_tools is the permission primitive the architecture needs, and PreToolUse hooks are a clean single integration point for everything we layer on (the Cerbos check, the Langfuse span emit, the Inngest event fire). Picking the Claude Agent SDK means writing ~50 lines of hook code, not ~500 lines of framework adapter. Every alternative imposes a more expensive wiring tax.

03 · What the SDK actually does for us 🔒

Five concrete jobs — and what we layer on top.

The SDK is intentionally narrow. Knowing exactly what it gives you (and what it does not) is the difference between leveraging it cleanly and accidentally fighting it.

1 · Hosts the agent loop

Model call, tool-call parsing, tool execution, result feedback, repeat. Context compaction built in.

2 · Speaks MCP natively

Points at our mcp-gateway Worker URL like any other MCP server. No translation layer.

3 · First-line permission gate

allowed_tools filters before a tool is even invoked. Cerbos is the second line, inside the hook.

4 · PreToolUse hook surface

One (agent, tool, args) callback where the gateway dispatch + audit emit + approval check live.

5 · Skills + prompt caching

Agent personas (Grant, Penny, Leo, Grace, Katharine) load as Skills. Caching keeps token cost down across runs.

What the SDK does NOT do — and what we layer in

Audit / proof of work. Layered in via Langfuse, called from the PreToolUse hook.

Permission policy beyond the allowlist. Layered in via Cerbos, called from the same hook.

Human-in-the-loop approval gates. Layered in via Inngest, triggered through the MCP gateway when an action is destructive.

Human-facing surface for the same actions. An HTML form on Cloudflare Pages that POSTs to the same Inngest event — identical code path.

04 · Implications you should plan for 🔒

The honest cost-of-being-wrong.

Every runtime choice has a tax. Here are the six the Claude Agent SDK will levy on you, ranked by what hurts most in a real pilot.

1 · Model lock-in

Agents are coupled to Claude. Tools are not — MCP is provider-neutral. If Anthropic ever falters or you decide to move to GPT or Gemini, migration cost is the runtime layer only, roughly one day per agent to rewire. Acceptable, but worth saying out loud before partners commit.

2 · June 15, 2026 pricing change

Starting 2026-06-15, programmatic Claude SDK usage starts drawing separate credits ($20–$200/mo depending on plan tier). Budget this per agent before pilots scale. At one-call-per-day per agent it is a rounding error; at fleet scale it adds up to real money.

3 · Single-vendor SDK velocity

Anthropic ships fast. The SDK was renamed from claude-code-sdk in mid-2025; MCP went GA; Skills landed; prompt caching changed shape twice. Budget ~half a day per quarter for SDK version bumps. The catalog cadence on /tools/ is Hot (quarterly) for exactly this reason.

4 · Weaker multi-agent orchestration than LangGraph

If you ever want Grant + Katharine to coordinate without human-in-loop — e.g. CFO and CRO jointly close a deal — you will bolt on a state machine. Likely an Inngest workflow, since Inngest is already in the architecture. Do not switch runtimes for this; layer on instead.

5 · Partner-copyability is cheap

A partner cloning this needs one Anthropic API key. That is the entire dependency. Cheaper than the GCP/Vertex alternative (project + billing + Vertex enablement + service-account setup) and easier than the OpenAI alternative if they want Claude-specific features (Skills, MCP, longer context).

6 · Hook-composition gotcha

The PreToolUse hook is the place where four concerns intersect: policy check, approval gate, audit emit, vendor MCP forward. Keep that hook short and well-tested — it is the load-bearing seam of the whole architecture. If it grows past ~150 lines, factor each concern into its own module before it ossifies. A partner who skips this will be debugging spaghetti six months in.
